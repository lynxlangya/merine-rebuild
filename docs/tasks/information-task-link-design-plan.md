# 信息流转与任务处置关联评估

2026-09-30。任务处置与信息流转已分别完成本地验收。本文件是第四阶段的后续实施计划，以下关联能力均未开发；本轮没有新增关联表、字段、按钮或空壳接口。

## 关联的业务价值与边界

一条情报可以成为多项任务的背景，用稳定情报 ID 追溯来源。每项任务仍须由有权限的人明确填写责任单位、办理要求、期限和预期结果。情报共享和单位签收不自动生成或承接任务；任务办结不改变情报状态，也不要求所有情报接收单位反馈。

最小关联包括“从情报创建任务”和“手动把任务结论回流到情报”。不合并两个模块的发起入口，不复制情报发送历史到任务，不开放整条任务明细，不加入情报池。

## 权限与传播边界

| 场景                         | 后续采用的规则                                                                                                                                         |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 从情报创建任务               | 同时具备情报查看、实际数据授权和任务创建权限。仅带入原始情报背景，任务责任、要求、期限、预期结果仍需显式填写。                                         |
| 选择任务责任单位             | 该单位必须已实际收到该情报；源头单位视为已参与。未收到时先独立走合法信息流转，不能在创建任务时自动共享、扩范围或跳级。                                 |
| 关联任务下发、重派、交接     | 新责任单位同样须已实际收到来源情报。将限制放在任务后端写入路径，候选列表给出不可选择原因，不能只限制创建入口。                                         |
| 查看关联                     | 每次重新校验两个模块的功能权限和数据范围。只有任务权限时，不返回情报原文、标题或编号；只有情报权限时，不暴露无权查看的任务编号、责任单位、数量或结果。 |
| 任务结论回流                 | 操作者须能查看相应正式结果，并具备目标情报写入权限。源头单位追加补充；非源头单位只能对自己已签收的具体回执反馈。不把非源头反馈升级为源头更正。         |
| 来源后来不可见或账号权限变化 | 关联不会保住旧权限；页面显示不可访问状态，接口不返回受限内容。历史关系保留，模块状态各自维护。                                                         |

任务背景中的人工描述本来就可能包含线索，关联会增加复制和扩散的便利。因此正式关联实现必须把“新责任单位已收到情报”的检查贯穿下发、重派和交接；仅在创建表单校验不能守住传播边界。

任务操作者不必有情报功能权限才能办理自己有权承担的任务，但关联原文入口仍按情报权限判定。任务结果的回流范围遵循既有情报规则：源头补充所有已接收单位可见，回执反馈仅沿对应发送链可见。提交前明确显示接收范围，由操作者手动选择适合共享的文字，不自动同步完整结果或办理记录。

## 建议的数据与接口改动

正式关联阶段只增加显式关系与回流留痕，保持 `task_order` 和 `intel_topic` 各自的状态及原文。以下是拟实施内容，不是现有接口：

- 一张来源关系表：情报 ID、任务 ID、建立单位/操作者/时间；一条情报对应多项任务，首版一项任务最多一个来源。加唯一约束与双向索引，无物理外键。
- 一张结果回流记录表：来源关系、正式结果、选定文字摘要、目标补充或反馈 ID、操作者/单位/时间与幂等键。不同手工选择可重复共享，同一次提交不能重复追加。
- 创建关联任务使用独立写用例：在同一事务内校验双方权限、情报实际送达、新任务目标合法性，创建任务与关系全部成功或全部回滚。通过模块显式公开能力协作，不从一个模块直接修改另一个模块的表。
- 结果回流使用独立写用例：重新校验任务结果和目标情报回执，调用现有补充或反馈能力，并记录回流关系。是否公开任务引用仍按查看者权限过滤；关联本身不授权。
- 接口路径、DTO、关系表命名及新按钮权限在关联实施设计时确定，然后按 Java → OpenAPI → TypeScript 生成契约。不能沿用“有情报查看权限即可创建任务”的隐式授权。

最小功能可采用 `intelligence:topic:create-task` 与 `task:handling:share-result` 两个新操作码，且必须同时检查现有任务创建、结果查看、情报补充或反馈权限。新权限需要显式赋予；不因菜单迁移自动扩大现有角色授权。权限码名称在实施前与既有任务权限清单核对。

## 后续实施顺序与验收

| 顺序 | 交付                                     | 验收门槛                                                                                           |
| ---- | ---------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 1    | 关联实施设计，核对两个模块公开能力与锁序 | 确定权限码、表、接口、事务边界和冲突原因；无重复状态机或空壳扩展。                                 |
| 2    | 来源关系及后端用例                       | 实际接收限制覆盖创建、下发、重派和交接；隔离 MySQL 验证全成功或全回滚、幂等与引用保护。            |
| 3    | 生成契约及“从情报创建任务”页面操作       | 原文保留，背景可追溯，责任/期限/结果要求显式填写；没有自动共享或任务承接。                         |
| 4    | 手动选择正式结论回流                     | 源头补充、非源头回执反馈两条路径分别验收；平行分支不出现另一分支的结论或受限任务引用。             |
| 5    | 跨账号验收与交付                         | 撤权、未收到、范围外目标、重复提交、并发失败均有真实证据；双方状态不联动，亮暗主题及既定视口通过。 |

现阶段不需要情报池即可完成上述关联。是否引入情报池，等独立流转与关联在实际使用中暴露出检索、发现或统一汇集的需求后再另行讨论。

已有链路与验收依据：[信息流转](information-flow-design-plan.md)、[任务处置](task-handling-design-plan.md)。
