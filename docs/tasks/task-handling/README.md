## 先分清三个对象

| 对象                     | 一句话理解                       | 示例                                                   |
| ------------------------ | -------------------------------- | ------------------------------------------------------ |
| 整单 `task_order`        | 发起单位交办的一件事             | 总队发起一次核查                                       |
| 分支 `task_branch`       | 需要一份明确答复的责任           | 温州、舟山分别承担一个根分支；温州再派大队时新增子分支 |
| 承办段 `task_assignment` | 某个单位在一段时间内承担这个分支 | 温州交接给台州，分支不变，但增加台州的承办段           |

**向下下发新增分支；退回、重新派发和平级交接沿用原分支，新增承办段。** 普通承接只修改当前承办段，不再新增一段。

`COMPLETED` 在整单上表示“已办结”，在分支和承办段上表示“已答复”。全部分支答复或撤回后，整单先进入 `AWAITING_CLOSE`；只有发起单位填写总体结论才变为 `COMPLETED`。

## 用一条任务串起三份图

总队发给温州、舟山两个单位 → 温州承接并提交 `NOT_FOUND` → 舟山承接前退回 → 总队说明原因撤回舟山分支 → 整单待办结 → 总队填写总体结论办结。

对照下面的数据变化阅读：

1. 创建：1 条整单、2 条根分支、2 条待承接段；新编号由 `task_no_counter` 分配。
2. 温州答复：新增 1 条 `task_result`，温州分支及其当前段变为 `COMPLETED`。
3. 舟山退回：原段变为 `RETURNED`，新增总队的 `IN_PROGRESS / RETURN` 段；分支仍是 `OPEN`。
4. 总队撤回：舟山分支及其当前段变为 `RECALLED`，不新增结果；此时整单进入 `AWAITING_CLOSE`。
5. 总队办结：整单写入 `conclusion`、`closed_by_user_id`、`completed_at`，并变为 `COMPLETED`。
6. 每个首次成功执行的写入意图都追加 `task_action`，并完成同事务内的 `task_command` 幂等记录；相同意图重放不重复写入。

## 阅读边界

- 库表图中的线是**逻辑引用**，本项目没有物理外键；引用与业务不变量由应用事务、锁、条件更新、唯一约束及回归检查共同维护。
- 图中的单位只是合成示例。此目录不保存业务正文、账号凭据或数据库快照。
- 图描述模块实现，不代表已经完成浏览器交互验收，也不代表全项目已有通用数据范围模型。
- 如果以后改变状态、API 或表结构，应按实际代码更新对应图；不要仅修改图而假定行为已经改变。
