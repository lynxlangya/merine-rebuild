# 扩展案例：上线半年后增加任务评分

[返回学习入口](README.md) · [现有库表关系](database.md) · [现有业务流程](business-flow.md)

记录日期：2026-09-28。本文整理一次围绕现有任务模块的问答，用于学习功能演进、历史兼容与扩展性设计。“上线运行半年”是假设场景；评分方案属于设计建议，尚未实施，也不代表业务规则已经确定。

## 问题

假设任务处置模块已经稳定上线并运行半年，现在希望增加评分功能，由总队对支队或大队的任务处置打分。

如果需要新增数据库字段、表，或者修改现有逻辑，应考虑哪些事情？上线后增加功能有哪些限制？在当前开发阶段，又应该为未来保留哪些扩展能力？

## 回答一：上线后可以改，关键是兼容已有事实与行为

数据库和代码可以继续调整，但新增功能必须兼容旧数据，并保持原有业务行为正确。对这个例子，倾向于把评分作为独立业务记录，关联已有办理责任。

现有的“整单、分支、承办段”划分已经提供了扩展基础。第一步应明确评分的业务含义，再决定字段或表结构。

## 回答二：先确定给谁的什么表现打分

| 评分含义                         | 对应当前对象             | 示例                                             |
| -------------------------------- | ------------------------ | ------------------------------------------------ |
| 评价整项任务的总体效果           | 整单 `task_order`        | 本次专项核查总体评价 90 分                       |
| 评价某项办理责任的最终答复       | 分支 `task_branch`       | 甲支队汇总答复 90 分，某大队具体核查答复 85 分   |
| 评价某单位某一段时间内的办理表现 | 承办段 `task_assignment` | 甲支队交接前表现 70 分，乙支队接续办理表现 90 分 |

例如，甲支队办理一半后交接给乙支队，最终由乙提交结果。如果只给这个分支记一个 90 分，不能直接认定甲、乙都得了 90 分。

因此，需要区分“最终答复质量”和“各单位的履职过程”。前者可以关联分支，后者需要定位到具体承办段。总队评价支队与大队时，也应明确是在评价不同层级各自的责任。

## 回答三：简单属性可以加字段，独立评分更适合加表

像“是否重点关注”这样的简单属性，可以直接新增字段。评分通常还涉及评语、评分人、评分单位、时间、修改原因和评分标准，是一项独立业务事实，更适合新增评分表，例如 `task_evaluation`，仍归任务模块管理。

假设首版规则是“总队对每条已答复的办理责任给出一份正式评分”，可采用以下最小设计：

- 关联 `branch_id`，保存分数、评语、评分单位、评分人和评分时间。
- 被评单位从正式结果对应的承办记录确定，避免按当前组织名称或列表显示值猜测。
- 用唯一约束保证每条责任只有一份正式评分；如果以后允许多个主体分别评分，应重新明确唯一性范围。
- 旧任务没有评分记录时显示“未评分”。**未评分不等于 0 分**，也要与“不适用”区分。

允许改分时，需要保存修改前后内容、修改人、时间和原因，并处理并发修改。评分标准会变化时，需要保存当时的标准版本及必要内容；仅保存版本号、却覆盖原标准，仍然无法解释历史分数。

这些都是待业务规则明确后实施的设计，不要求现在提前建表或预留字段。

## 回答四：评分要有自己的权限与状态规则

### 总队身份不等于能评价所有任务

当前总队作为发起单位，可以查看自己发起任务的全部分支，包括下级大队办理情况。支队独立发起的任务，不会仅因总队是上级就自动对总队开放。

如果要求总队统一评价所有下级任务，需要明确扩展数据范围，并规定谁能评分、谁能查看分数和评语。新增按钮不能代替后端的操作权限与数据范围校验。

### 评分条件不同于办理条件

现有 [TaskService](../../../apps/api/src/main/java/com/merine/rebuild/task/TaskService.java) 的 `locked()` 要求整单和分支均为 `OPEN`。办结后评分不能直接套用这个方法，也不能为了评分放宽所有办理操作的限制。

首版可考虑：**已提交正式答复的责任可以评分；评分独立保存，不改变答复内容、办理期限和办结状态。**

实施前还需明确：撤回的责任是否参评、允许多久内评分、能否修改、被评单位能否查看。若要求“全部评分后才能办结”，就改变了主流程，必须同时确定旧任务是否适用，避免已有任务被新规则卡住。

## 回答五：数据库升级要考虑历史数据、发布与恢复

“直接在库里加字段”应落实为可重复、可核对的迁移，遵循现有[数据库规则](../../rules/database.md)。

| 需要考虑的事   | 本案例中的处理原则                                                                       |
| -------------- | ---------------------------------------------------------------------------------------- |
| 迁移记录       | 追加新的 Flyway 迁移，不改已经执行的历史迁移，不只在某个库里手工修改                     |
| 历史评分政策   | 明确旧任务能否补评，或者只评价功能启用后下达的任务；不能自动填默认分数冒充评价           |
| 必填字段与约束 | 给已有记录新增必填字段或收紧约束前，先检查、按可靠依据回填并验证；未知内容不能随意补造   |
| 发布兼容       | 通常先增加兼容旧程序的新表或字段，再发布后端、前端；删除旧字段或收紧约束放在完成切换之后 |
| 程序回退       | 验证旧程序能否在新结构上运行；回退程序时一般保留已经产生的评分数据                       |
| 迁移失败与恢复 | 上线前准备并验证备份、恢复方案；MySQL 多条 DDL 不能假定会像普通业务事务一样全部回滚      |
| 引用完整性     | 本项目没有物理外键，新关联继续由应用事务、引用检查、索引和回归验证共同保证               |

新增评分表对旧数据的侵入较小，但仍应检查迁移耗时、索引和查询影响。接口增加评分内容后，也要明确无评分时的返回值，按[后端契约规则](../../rules/backend.md)重新生成类型并核对实际响应，不能靠手改前端类型完成升级。

## 回答六：统计口径、并发和验收同样重要

### 统计口径

总队给支队 90 分，又给其下两个大队 80、100 分，直接求平均可能把同一项工作在上下两级重复计算。按单位统计或排名前，需要明确：

- 按任务下达、答复，还是评分时间归入统计周期？
- 未评分、不适用、撤回分别怎样处理？
- 交接前后的成绩归哪个单位？
- 不同评分标准下的分数是否能够直接比较？
- 单位调整后，历史成绩按当时归属还是现在归属统计？

这些口径会决定需要保存哪些历史信息，不能等报表出现偏差后再凭当前数据推测。

### 并发与必要验收

两名总队人员同时评分，不能让后一次提交静默覆盖前一次结果。重复提交、并发改分、评分和修改记录一起成功，都需要明确处理。

实施时至少验证：

1. 空库迁移与代表性的旧版本合成数据升级均正常，旧任务仍可查看和办理。
2. 合法人员可评分，无权限或超出数据范围的请求被拒绝。
3. 重复提交不产生重复评分，并发冲突有明确结果。
4. 修改可追溯，失败不会只保存分数却漏掉修改记录。
5. 新增关联查询不造成任务列表重复、数量错误或明显变慢。
6. 页面、API 和数据库中的评分、未评分状态及可用操作一致。

数据库行为在隔离的真实 MySQL 中验证；编译成功和页面出现输入框不能替代上述验收。

## 回答七：当前开发阶段应保留什么扩展性

| 现在值得做好                             | 对后续扩展的价值                       |
| ---------------------------------------- | -------------------------------------- |
| 保留整单、分支、承办段的稳定标识         | 新增评分可以准确关联，不必重建责任关系 |
| 保留原期限、实际承接和答复时间、交接过程 | 支持有依据的时效评价与责任归属         |
| 正式结果和办理历史不被静默覆盖           | 后续评分能够对应当时的事实             |
| 在后端集中校验权限、数据范围与业务条件   | 新功能沿用清晰的授权边界               |
| 保持可执行的迁移、接口契约和关键回归     | 能验证升级是否破坏已有功能             |

**半年后可以新增字段，但半年内没有记录的事实，无法靠新增字段补回来。** 如果将来可能按响应速度评分，现在保存的承接时间就有价值；如果从未记录实际工作量，就不能事后凭空计算工作量得分。

目前无需提前增加备用字段、通用扩展 JSON 或评分规则引擎。等需求明确后，可以在任务模块中增加职责清楚的评分用例和页面区域。当前重点是把已有责任、时间与结果记录准确，并保持它们的含义稳定。
