## 业务边界

信息流转让其他单位知道线索、补充判断和继续共享，没有责任承接、核查期限、必交结果或办结。情报只有 DRAFT（草稿）、PUBLISHED（已发出）；签收与反馈是独立事实，阅读原文不另做记录。

发送关系允许直属上下级、同一总队下的支队互发。大队仅可向直属支队上报，不允许同支队或跨支队的大队之间直发共享；候选和后端提交使用同一判定，历史送达保留。拒绝跨级直发。当前单位及目标单位须启用。

原发起单位在单位树上勾选允许传播的具体单位，可一并选择整棵子树。客户端将勾选展开为单位编码，服务端首次发送再次按当前组织校验并固化单位 ID 与名称快照。草稿保存范围和首次目标，发送前可修改；发出后范围固定，新增单位不会自动入选。扩大范围需另发情报并注明原编号。

范围必须能从源头通过合法关系到达，所有必经中转单位都须在范围内。服务端在范围加源头组成的图中检查可达性；缺失中转支队则拒绝并提示显式补齐，不自动扩大范围。首次接收单位还必须与源头直接具备合法发送关系。源头本身可继续发送；范围不是查看授权，只有源头和实际收到情报的单位能查看。

签收前可查看原文，不记录个人阅读。详情 GET 仅查询，不写入业务记录。单位签收绑定一次接收回执，签收后才能对该回执反馈或继续共享。不同路径分别形成回执、分别签收；同一父回执到同一目标不重复送达。源头后续发送仅面向尚未收到该情报的单位；列表按情报合并，待签收表示本单位至少有一份未签回执，已签收表示本单位所有回执均已签收。

反馈绑定具体回执；反馈单位、原发起单位及该回执发送链上的上游单位可见。平行分支不能查看另一分支反馈。历史按回执链过滤：查看自己的送达路径、自己发送的各条后续路径；共同祖先的一次多目标批次只展示当前单位有权看到的回执，不暴露平行目标、数量或反馈。源头可看全部发送链。传播范围清单只向源头展示，接收方仅知道当前合法共享候选。

发出后标题、正文不可覆盖；源头单位通过 SUPPLEMENT（补充）或 CORRECTION（更正）追加说明，所有已接收单位均能查看。不强制反馈，反馈不形成处置任务。

```mermaid
flowchart LR
  A[源头保存草稿与传播范围] --> B[首次发送 固化范围]
  B --> C[接收单位阅读]
  C --> D[单位签收某次回执]
  D --> E[可选 追加反馈]
  D --> F[可选 继续共享]
  F --> C
  B --> G[源头追加补充或更正]
  G --> C
```

## 模型及不变量

独立 `intelligence` 模块拥有 `intel_` 表。ID 全部以十进制字符串返回。编号采用 QB-日期-六位流水，草稿即获得稳定编号；转发永远不复制情报。

| 表                   | 事实与约束                                                                                                  |
| -------------------- | ----------------------------------------------------------------------------------------------------------- |
| intel_topic          | 编号、源头单位/用户快照、标题、正文、状态、草稿版本、创建/发布时刻。                                        |
| intel_scope_unit     | 情报允许传播的单位 ID 和名称快照，(topic,unit) 唯一；首次发布后不可修改。                                   |
| intel_draft_target   | 草稿保存的首次目标，发布后仍保留创建意图。                                                                  |
| intel_send           | 一次发送批次；原发发送 parent_receipt_id 为空，继续共享明确来自哪次回执；保存发送单位、操作者、说明与时间。 |
| intel_receipt        | 每个发送目标的一份回执，(send,unit) 唯一；单位签收人/时间及单位名称快照。                                   |
| intel_read           | 历史个人阅读记录表；功能已移除，V29 保留既有数据，不再由应用查询或写入。                                    |
| intel_feedback       | 回执关联的追加反馈及单位、用户、时间快照；不覆盖旧反馈。                                                    |
| intel_supplement     | 源头追加的补充/更正及单位、用户、时间快照。                                                                 |
| intel_command        | 单位、动作、幂等键、请求摘要和结果情报 ID；同键同意图重放，不同内容 409。                                   |
| intel_number_counter | UTC+8 业务日期的编号计数器，事务内递增，失败回滚。                                                          |

不建物理外键；所有引用有索引、注释和悬空巡检。单位删除通过 `IntelligenceUnitUsageLookup` 的锁定读拒绝历史引用。组织调整不扩大范围、不抹历史，后续发送按当时实际关系再次校验。

写入事务使用 READ_COMMITTED。先锁系统授权锚点与相关单位（按主键），再锁情报，最后写关系和命令。组织只三级且 50 个参考单位，首版写入锁定组织行集以获得一致的关系图，代价是不同情报写入短暂串行；无网络调用持锁，未来有实际吞吐证据再缩小锁集。多目标发送全部成功或全部失败。并发签收只记录首个签收人/时间。草稿版本冲突 409。幂等事务内占位，失败无半成品；重放仍检查功能权限和实际查看授权。

## 页面、权限与接口

沿用 `/collaboration/flows`，详情 `/collaboration/flows/:topicId`。列表有“我收到的”（全部、待签收、已签收）与“我发出的”（全部、草稿、已发出），搜索标题/编号。新建先保存草稿再发送；表单标题 160 字、正文 4000 字、范围树、首次接收单位及发送说明（1000 字）。详情显示原始情报、源头说明、可见回执链和反馈；每份本单位回执分别签收、反馈、共享。失败保留输入和幂等键，成功才清空。GET 不改变签收状态。无内容的补充卡片不展示，已发出后不下发修改草稿动作；规则说明放到必要的禁用提示，不在页面常驻。

功能权限为 `intelligence:topic:read|create|update|send|sign|feedback|forward|supplement`。菜单、按钮与接口同源；系统管理员只有功能权限，仍需单位参与。后端返回 `allowedActions`（code、enabled、reasonCode、reason），不具备权限或单位资格时不下发，前置状态不足时返回禁用原因，写入与动作提示共用判定。前端仅映射显示名称。

| 接口                                                              | 作用                                                                                                                        |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| GET /api/intelligence-topics                                      | 分页列表，SQL 内按当前单位限定；数量同范围，不泄漏其他单位。                                                                |
| GET /api/intelligence-topics/{id}                                 | 详情，只读；无关单位及无数据范围管理员 404。                                                                                |
| GET /api/intelligence-topics/unit-options                         | 创建/编辑返回组织树数据与合法首次目标；send/forward 须带 topicId，forward 另带 receiptId 并校验该回执，候选须在冻结范围内。 |
| POST /api/intelligence-topics                                     | 新建草稿。                                                                                                                  |
| PUT /api/intelligence-topics/{id}                                 | 带 version 修改草稿；发布后拒绝。                                                                                           |
| POST /api/intelligence-topics/{id}/send                           | 首次发送/源头向未收到的合法单位继续共享；输入目标及说明。                                                                   |
| POST /api/intelligence-topics/{id}/receipts/{receiptId}/sign      | 显式单位签收。                                                                                                              |
| POST /api/intelligence-topics/{id}/receipts/{receiptId}/feedbacks | 可选追加反馈。                                                                                                              |
| POST /api/intelligence-topics/{id}/receipts/{receiptId}/forward   | 由已签回执继续共享，同一回执到同一单位最多送达一次。                                                                        |
| POST /api/intelligence-topics/{id}/supplements                    | 源头追加补充/更正。                                                                                                         |

写接口要求 Idempotency-Key，身份、单位、状态、时间由服务端确定。Java DTO → 本地 OpenAPI 快照 → TypeScript 类型，不手改生成文件。新迁移同时维护正式菜单及默认菜单恢复清单；演示赋权仅通过本地合成账号专用的 `scripts/fixtures/information-flow-demo.sql`，不在应用迁移中扩大已有角色授权。

## 关联扩展入口

稳定情报 ID、原文与发送历史用于关联追溯。一条情报可产生多项任务，任务独立填写背景摘要、责任单位、要求、期限与预期结果。共享/签收不自动发任务或承接任务。结果由有权限的人手动共享至具体反馈或源头补充，关联不开放受限任务明细，不改变双方状态。V30–V32、公开能力和跨账号证据见[关联设计](information-task-link-design-plan.md)。

## 页面复核后的调整

2026-09-30。阅读记录没有新增业务价值，已完整撤下按钮、接口、DTO、权限与默认菜单；原表只保留历史数据。页面只保留原文、签收状态、实际流转记录和反馈，不重复铺陈业务规则；有补充或更正才显示卡片，已发送的草稿按钮隐藏。

源头原来的“再次发送”用于覆盖首次发送时没有选择的单位，不应变成给同一单位反复新增待签回执。现改为“共享给其他单位”，候选与写接口都排除已收到情报的单位；没有合法新接收单位时隐藏入口。接收方从同一个父回执向同一目标也只能共享一次；不同路径仍保留独立回执和签收。多目标含重复目标时全部拒绝，客户端同一请求键的重放仍返回原结果。

本轮浏览器使用新合成情报 `QB-20260930-000004`（ID 4）：总队首次发给宁波后，新共享候选只剩温州；发给温州后入口消失。温州未签收可查看，反馈与共享禁用；签收后隐藏签收按钮并启用这两个动作，全程没有阅读按钮和空补充卡片。两种主题、两个既定视口均复核，页面无横向溢出。15 项信息流转后端回归、完整检查与构建通过；另补测不同请求键并发发送只产生一份回执、重复目标批量发送全部回滚。

## 代码审查后的修复

2026-09-30。修复三个问题：幂等键按实际提交的规范化命令复用，网络等错误导致结果不明时保留原命令与请求键，仅允许重试原提交；已选的停用单位可以从草稿范围中取消，未选的停用单位仍不可新增；范围缩小或单位停用后，首次目标自动移除失效选择，并在表单内校验。

前端动作名称集中维护，请求使用明确的动作及 DTO 类型，提交和缓存更新收拢到专用 Hook，成功写入直接使用返回详情，不再紧接着重复 GET。后端一次加载并索引回执、范围、已送达目标和反馈，详情组装不再逐回执重查数据库或反复遍历整条发送链。权限、签收及多路径业务语义保持一致。

新增 7 项前端和 2 项真实 MySQL 回归。响应丢失通过 HTTP 客户端的替身传输模拟；真实 MySQL 验证同键重放、停用范围移除后发布，以及同一单位反复经过时的分支反馈隔离。完整检查与构建通过。

浏览器新增合成情报 `QB-20260930-000005`（ID 5）：范围选择宁波和温州、首次目标选择宁波，再取消宁波范围，首次目标自动清空，候选只剩温州；空目标被表单拒绝。改选温州后完成保存、编辑、发送、温州签收与一次反馈。亮暗主题的 1440×900、1366×768 表单均复核，提交区可见、无横向溢出。停用单位场景由范围模型与真实数据库回归覆盖，本轮未停用开发库单位。
