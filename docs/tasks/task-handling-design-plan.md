# 任务处置：数据模型、交互与开发计划

学习入口：[任务处置图解](task-handling/README.md)（模块架构、业务流程与库表关联，按当前实现整理）。

> 状态：2026-09-27 已补充可用操作契约、显式办结、退回撤回与可读编号，待用户界面验收。本文保留设计依据与验收口径；第 9 节列出实际落点。总队/支队只向直属下级下发，支队之间可平级交接，大队之间不可交接；支队交接须先由目标支队确认承接，再由总队批准并确定新期限。若业务规则改变，须同步改状态、库表、接口和验收。

## 1. 业务目标与不变量

任务处置是要求接收单位承担一件事并交付明确结果。页面必须回答：任务由谁发起、每个接收分支当前谁负责、何时承接、做过什么、为何退回或交接、最终结果和期限是什么。

1. **直属下发**：总队可同时下发给一个或多个直属支队；支队可同时下发给一个或多个直属大队。总队不能直接给大队；大队不能下发；任何逆向、跨级或非直属“下发”都拒绝。一次多目标下发全成功或全失败。
2. **平级转发只允许支队之间**：仅已承接、当前负责的支队可向另一支队发起交接；大队间不提供转发入口或接口。支队交接不产生新的结果分支，仍是一条责任；甲此前工作和原期限保留。交接生效前甲仍负责，生效后乙负责，甲不再为同一分支另交最终结果。
3. **大队跨辖区反馈**：支队派给 A 大队，A 查明事项进入 B 大队辖区时，A 提交已做工作、依据、去向及未完成部分；支队决定是否给 B **另发任务并单独确定期限**。A 不直接把剩余时限转嫁给 B。
4. **结果与成功不同**：正式结果可以是目标达成、经核查未发现、部分完成、转出辖区或无法核实。全部责任分支已答复或已撤回后，整单进入待办结，由发起单位填写总体结论后显式办结；“流程已办结”不等于“业务目标已达成”，页面同时展示结果类型。承接、进展、退回和交接申请均不算正式结果。
5. **责任不可静默覆盖**：发出后的要求、原期限、历史责任单位和结果不得普通编辑覆盖；每次承接、退回、申请、同意、批准、拒绝、结果和期限调整都有操作者与时间。单位是责任主体，用户是具体操作人。

首版不做附件、催办推送、导出、AI、任务取消和真实业务档案关联；示例中的船舶、嫌疑人员资料仅以合成文本验证，不把真实个人资料导入本地。信息流转模块的签收/反馈/办结状态不直接复用。

## 2. 两种责任关系及示例

**向下下发产生新责任分支；支队平级转发只更换既有分支的承办单位。** 一条分支可以有多段历次承办记录，但最多一条当前有效承办记录，最终只有一份正式结果。

例一：总队建立任务 T，同时发甲、乙支队，得到分支 B1、B2。甲在 B1 下发给直属 A、B 大队，得到子分支 B1.1、B1.2；甲仍负责汇总 B1。A 若查明目标进入 B 的辖区，应提交 B1.1 的调查结果。甲决定是否另建关联的新任务给 B，不能把 B1.1 改派给 B。A、B 的子分支均有结果后，甲才能提交 B1 的汇总结果。

例二：乙支队承接 B2 后查明主要处置辖区属丙支队。乙提交**交接申请**，写明已经做的事、证据、原因和申请时间；丙先确认愿意承接，总队再批准并确定丙的新期限。批准时乙的承办段结束，丙在**B2 原分支**接续办理；不复制 B2，也不要求乙和丙各交一份最终结果。拒绝或尚未批准时乙仍负责。总队对乙早晚承接、何时申请、何时交接均可复核。

例三：支队给 A 大队两天期限，A 第二天才承接，下午发现事项已在 B 辖区。A 的承接时间和原期限不变；A 提交如实结果。如果任务仅要求查明去向，这可以是达成目标；如果要求完成后续处置，则结果标为部分完成或需后续办理。支队若向 B 发新任务，必须给 B 新期限，并以来源结果关联两项任务；B 不承接 A 剩余的半天。

## 3. 截止时间与支队交接规则

- `task_order.initial_due_at` 保存初次要求的整单期限，永不改写；`current_due_at` 是由任务发起单位明确调整后的整单期限。支队间交接涉及总队发出的任务，因此由总队决定是否延期。各承办段独立保存其被要求的 `due_at`，旧承办段的期限不随交接变更。页面并列显示“原期限”和“当前批准期限”，逾期按各段实际承担的期限判断，不能因改期抹掉曾经逾期的事实。
- 正常向下下发时，子分支期限由发送单位明确填写，须晚于创建时刻且不得晚于父分支当前承办期限；直接从任务发起单位创建的一级分支不得晚于整单当前期限。系统不凭剩余半天自动给新单位设半天期限；若剩余时间不够，承办单位应反馈上级，首版由有权单位另建后续任务。首版仅在总队批准支队交接时支持整单延期，不提供独立的通用改期入口，也不硬编码“必须提前 N 小时下发”的考核阈值。
- 支队交接申请只允许一个目标支队；仅适用于原本由总队下发、当前由支队承办的分支。必须填原因、已做工作、证据说明和需继续做的事。存在尚未办结的直属下级子分支时，不允许申请，以免下级办理失去汇总责任。不能交给自己、停用单位、该分支当前负责单位，或曾经承办过同一分支的支队，以免甲 → 乙 → 甲循环推责。
- 丙支队可同意或说明原因拒绝。同意时必须填“从正式交接生效起，至少需要多少办理时间”（分钟数，正整数），而非只答复一个脱离批准时刻的绝对日期；这是丙的承接条件。同意尚未转移责任。总队批准时指定的新期限必须晚于批准时刻，且至少满足丙确认的办理时长；若总队不能接受该时长，应拒绝申请，不能缩短后强行交接。批准还须校验任务仍为 `OPEN`、丙仍可接收、乙仍是当前责任单位、申请未撤回、子分支均已结束；在同一事务将乙承办段置为 `TRANSFERRED`，创建丙的 `IN_PROGRESS` 承办段，更新分支指针并记录期限变化。丙的承接人为其同意申请的用户，`accepted_at` 为总队批准时刻；责任从批准时开始，不追溯到乙申请或丙同意之时，也不要求丙再点击一次“承接”。
- 若丙的新期限晚于整单 `current_due_at`，总队在批准时须一并明确延长整单期限和理由；`initial_due_at` 保留。其他并行分支的承办期限不因整单延期自动改变。丙的新期限必须晚于批准时刻，不得从乙旧期限直接复制。审批拒绝、丙拒绝或申请撤回后乙继续负责，乙可以提交结果或重新申请；申请中乙仍可办理并追加进展，但不能继续向下下发、再次申请交接或提交最终结果，除非先撤回申请，避免审批与办结竞态。
- 交接申请在原期限前后均可提出，但不自动暂停倒计时或免责。乙的承接时间、原期限、申请时间、丙答复时间、总队决定时间单独展示；是否构成延误由业务依据这些事实判断，不让系统把“转发”当作自动合格。

## 4. 状态机、退回与撤回

| 对象                             | 状态                                                                                                     | 允许的后续动作                                                                                                                 |
| -------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 整单 `task_order`                | `OPEN` / `AWAITING_CLOSE` / `COMPLETED`                                                                  | 全部分支答复或撤回后进入待办结；发起单位填写总体结论再办结，不取消、不重开。                                                   |
| 分支 `task_branch`               | `OPEN` / `COMPLETED` / `RECALLED`                                                                        | 已答复必须有唯一正式结果；已撤回没有正式结果。交接、退回、重新派发不换分支 ID。                                                |
| 承办段 `task_assignment`         | `PENDING_ACCEPT` / `IN_PROGRESS` / `RETURNED` / `TRANSFERRED` / `REASSIGNED` / `COMPLETED` / `RECALLED`  | 当前待承接段可以承接或退回；普通办理段可以记录进展、派发、交接或交结果；退回接回段只能记录进展、重新派发或撤回。结束段不可写。 |
| 交接申请 `task_transfer_request` | `AWAITING_TARGET` / `AWAITING_ISSUER` / `APPROVED` / `TARGET_DECLINED` / `ISSUER_REJECTED` / `WITHDRAWN` | 申请 → 目标支队同意或拒绝 → 总队批准或拒绝；生效前申请方可撤回。每分支最多一条未决申请。                                       |

**承接前退回**仅用于三种情况：`WRONG_TARGET` 派错单位、`NOT_OUR_DUTY` 不属本单位职责、`UNCLEAR_REQUIREMENT` 要求不明确。当前 `PENDING_ACCEPT` 接收方必须选择启用的原因并填写说明（最多 1000 字）；非法或已停用原因拒绝。原段置 `RETURNED`，在该段保存 `end_reason_code` 与 `end_reason`；同分支新增发送单位的 `IN_PROGRESS`、`source_action=RETURN` 段，责任回到发送方。这不是下级向上级发新任务，也不是正式结果。

接回方二选一：**重新派发**给一个合法直属下级，或者填写原因**撤回分支**。重派目标排除这条分支上所有退回过的单位，不只排除最近一次退回方；同一分支可以经历多次退回和重派，原段完整保留。不允许普通向下派发或用 `UNABLE_TO_VERIFY` 等假结果收尾。撤回将当前段与分支置 `RECALLED`，说明写入段结束原因和 `RECALL` 动作；分支 `completed_at` 保持 NULL，撤回时间取承办段 `ended_at`。撤回前仍检查无未决交接和未结束下级。

重派仍遵守直属关系和父期限；当前段期限不晚于当前时间时，派发与重派都返回 `DUE_PASSED`。因此退回段期限已过时只能撤回，后续确有办理要求再另建任务。承接后发现辖区变化不能退回；大队提交真实结果，由支队决定后续任务；支队可按第 3 节申请平级交接。

正式结果固定为 `FULFILLED` 目标达成、`NOT_FOUND` 经核查未发现、`PARTIAL` 部分完成、`OUT_OF_JURISDICTION` 转出辖区、`UNABLE_TO_VERIFY` 无法核实。提交须填办理经过及结论（各最多 4000 字）；转出辖区必须选择建议后续单位，任何结果都不能建议本单位。建议单位来自全部启用单位（排除本单位），只作为线索，不自动创建任务。结果取值集合由代码与数据库 CHECK 固定，字典维护标签与可选性。

普通办理段提交结果前须无未决交接、无 `OPEN` 子分支；同一事务写唯一结果、结束承办段并将分支置 `COMPLETED`。答复或撤回后，若整单不再有 `OPEN` 分支，整单仅进入 `AWAITING_CLOSE`。发起单位有创建权限的用户填写最多 4000 字总体结论，通过独立办结接口写入结论、办结人、办结时间及 `CLOSE` 动作；所有参与单位可看结论和办结记录。`OPEN` 时办结按钮禁用为 `BRANCHES_OPEN`，已办结不再下发。办结流程上线前自动办结的旧任务不改写，结论为空时明确显示历史原因，旧的“退回后发送单位交结果”仍按历史事实展示。

## 5. 核心库表与约束

业务 owner 为任务处置模块，表名前缀 `task_`。以下是实施字段清单，不是可直接执行的 DDL。所有新表和字段按项目约定写有效 COMMENT，主键为 BIGINT、API ID 为十进制字符串、真实时刻用 UTC `DATETIME(6)`；状态用稳定 code，不用显示中文或 Java ordinal。没有物理外键，引用由写用例锁定校验并纳入悬空引用巡检。迁移只能新增 Flyway 版本，不改已执行文件。

| 表                      | 事实与唯一写入 owner                         | 主要字段、唯一性                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ----------------------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `task_order`            | 一项任务，任务模块                           | `id`、全局唯一 `task_no`、`issuer_unit_id`/`issuer_user_id`、`issuer_unit_name_snapshot`、`title`、`instruction`、`expected_result`（交付目标）、`initial_due_at`、`current_due_at`、`status`、`completed_at`、可空 `conclusion`/`closed_by_user_id`、`version`、可空 `source_result_id`（后续任务的来源）、创建/修改时间。发出后要求、原期限和发起单位名称快照不可普通编辑。                                                                                                                                                                                       |
| `task_branch`           | 一个下发目标形成的结果义务，任务模块         | `id`、`task_id`、可空 `parent_branch_id`、`origin_from_unit_id`/`origin_to_unit_id`、`instruction_snapshot`、`expected_result_snapshot`、`current_assignment_id`、`status`、`completed_at`、`version`、创建时间。初次下发的原始发送与接收单位不改写；当前负责单位从当前承办段读取。                                                                                                                                                                                                                                                                                 |
| `task_assignment`       | 同一分支的一段责任，任务模块                 | `id`、`branch_id`、可空 `previous_assignment_id`、`from_unit_id`/`to_unit_id` 及各自发送时的单位名称快照、`source_action` (`DOWNWARD`/`RETURN`/`REASSIGN`/`PEER_TRANSFER`)、`due_at`、`status`、`accepted_by_user_id`/`accepted_at`、可空 `ended_by_user_id`/`ended_at`/`end_reason`/`end_reason_code`、`version`、创建时间。一个分支最多一个活跃段；只有交接批准、退回或重新派发能换当前段。单位后来改名不改变历史交接记录的显示。                                                                                                                                 |

| `task_result`           | 分支唯一正式结果，任务模块                   | `id`、`branch_id` 唯一、`assignment_id`、`outcome_code` (`FULFILLED`/`NOT_FOUND`/`PARTIAL`/`OUT_OF_JURISDICTION`/`UNABLE_TO_VERIFY`)、`handling_detail`、`conclusion`、可空 `suggested_unit_id`、`submitted_by_user_id`/`submitted_at`。`assignment_id` 必须是该分支当前承办段；结果不可更新/删除。                                                                                                                                                                                                                                                                 |
| `task_action`           | 追加式业务历史，任务模块                     | `id`、`task_id`、可空 `branch_id`/`assignment_id`/`transfer_request_id`、`action_code`、`actor_unit_id`/`actor_user_id`、可空 `target_unit_id`、可空 `old_due_at`/`new_due_at`、可空 `note`、`occurred_at`。批准交接若同时延长整单期限，要分别记录“交接获批”和“整单延期”两条动作，各自的前后期限有明确对象；不用自由文本代替结构化时间。                                                                                                                                                                                                                            |
| `task_command`          | 可重试写入的幂等结果，任务模块               | `id`、`actor_unit_id`、`action_code`、`idempotency_key`、`request_digest`、`task_id`、可空 `branch_id`、`created_at`；唯一 `(actor_unit_id, action_code, idempotency_key)`。同 key/同语义返回原结果，不同语义 409；重放前仍检查当前访问权。                                                                                                                                                                                                                                                                                                                         |

新任务编号采用 `RW-YYYYMMDD-NNNN`：`task_no_counter(counter_date DATE PRIMARY KEY, last_seq INT)` 按 `Asia/Shanghai` 自然日分配，`last_seq > 0`。创建事务在单位引用锁与幂等占位之后执行 `INSERT ... LAST_INSERT_ID(1) ON DUPLICATE KEY UPDATE last_seq=LAST_INSERT_ID(last_seq+1)`，立即读取序号，再插入任务。同日并发在计数行串行，事务回滚不消耗序号，幂等重放不取号；超过 9999 自然扩为五位。旧 `TASK-…` 编号保持不变，不回填。

`task_branch.current_assignment_id` 必须指向同一分支的最新承办段；`task_result.assignment_id`、交接申请的 `from_assignment_id` 也须匹配分支。数据库级唯一约束守住 `task_no`、结果每分支唯一、同分支一条活跃承办段及同分支一条未决交接申请；后两项可用只对活跃状态产生非 NULL 值的生成列 + 唯一键，实际语义需在隔离 MySQL 验证。创建/换责还要锁任务行串行化，不以普通 SELECT 后无条件 UPDATE 保证并发。`CHECK` 守住状态 code、版本非负和基本时间关系；父子组织、身份、数据范围及整单办结属于跨行规则，由事务用例保证。

主要列表和历史索引从查询推导：`task_order(issuer_unit_id, created_at, id)`、`task_branch(task_id, parent_branch_id)`、`task_assignment(to_unit_id, status, due_at, id)`、`task_assignment(branch_id, id)`、`task_transfer_request(target_unit_id, status, requested_at)`、`task_action(task_id, occurred_at, id)`；各关联列有索引。列表先限定授权分支再分页/计数，避免一任务多分支 JOIN 放大 `total`。用合成数据与 EXPLAIN 复核执行计划，不预设大规模性能结论。

## 6. 权限与数据范围

建议功能码：`task:handling:read`、`task:handling:create`、`task:handling:accept`、`task:handling:progress`、`task:handling:dispatch`、`task:handling:return`、`task:handling:submit-result`、`task:handling:transfer-request`、`task:handling:transfer-respond`、`task:handling:transfer-decide`。最后一项只供总队在其发出的支队分支上执行；按钮与后端用例必须同时判权。代码常量、迁移、菜单节点和默认菜单恢复清单保持一致；不提供大队平级转发权限/接口。内置系统管理员的功能码不自动赋予全部业务任务数据范围。

直接参与范围：任务发起单位可看本任务全部分支；当前承办单位可看任务要求、自己负责的分支及其下级结果；曾经承办过的单位可看自己的历史承办段、交接记录和该分支最终结果，但不能继续写。候选丙支队在交接批准前只可看到作出接收决定所需的任务摘要、要求、剩余工作及申请证据摘要，不开放其他无关分支；批准后获得当前分支及必要下级结果。总队作为支队交接的决定者可看该任务与申请全貌。列表、详情、计数、候选单位、交接决定和所有写入都在服务端校验操作权限与数据范围；无关单位猜 ID 返回一致 404。单位筛选只能收窄可见集合。

合法目标按实时 `sys_unit.parent_id` 和层级验证：普通下发必须 `target.parent_id = sender.id` 且层级 +1；支队交接的甲、丙必须都是启用的 2 级支队、同属总队，且不是同一单位。单位停用、账号不属于操作单位、原任务/分支不在参与范围或目标非法均拒绝。已有单位管理对活跃任务涉及的单位删除、修改上级/层级时须联动拒绝；名称修改不回写历史名称快照。任务模块已在服务端实施上述参与单位与分支范围；系统管理权限不扩大任务范围。

历史范围：`CREATE`、整单 `EXTEND_DUE` 和 `CLOSE` 对所有能看详情的参与单位可见；创建动作的单位数说明仅发起单位可见。延期说明仅发起单位或能完整查看该交接分支的单位可见；另一分支的参与方仅看到整单前后期限，不能看到交接动作或原因。其他动作沿用既有分支过滤，不扩大承办段可见范围。新显示的发起人、操作人、提交人和办结人按用户 ID 查询 `sys_user.display_name` 当前值，查不到返回 NULL；改名会改变历史显示。发起单位与承办段单位名仍用原有快照，办理记录单位名沿用当前名称。

`close` 默认复用 `TASK_CREATE`，`recall` 默认复用 `TASK_DISPATCH`；权限码仍用 `PermissionCodes.TASK_*`。返回操作列表不代替写入授权，所有入口重新校验。

## 7. 页面、表单与接口

沿用 `/collaboration/tasks` 路由，把空骨架替换为：

- **列表**：`待我单位承接`、`我单位办理中`、`我单位发起`、`待我单位回应的支队交接`、`待总队决定的交接`、`待办结`、`已办结`。一行展示任务编号、标题、原/当前截止时间、当前责任单位（可多个分支）、我单位状态、交接待办、最近动作。逾期提示按每段责任期限计算。
- **详情**：独立路由 `/collaboration/tasks/:taskId`，保留列表分类与页码。抬头信息行展示编号、发起单位、发起人、发起时间与期限；下方是办理结论、我单位待办、任务概况、各单位树表与默认收起的历史。汇总只统计当前可见的根分支，答复加撤回达到总数即全部结束，结果类型与按期/逾期分开展示；不重复在树表头展示汇总。分支采用 640px 只读抽屉，显示结果提交人、交接申请方、退回原因标签及说明、撤回原因；操作复用页面弹窗，框最多嵌套两层。时间统一 `YYYY-MM-DD HH:mm`、UTC+8、不可折行，日期选择器不带秒；交接时长按小时或天录入，接口仍用分钟。
- **表单**：创建/继续下发可多选直属下级并明确期限；承接是独立确认；承接前退回原因选择与说明必填；进展仅追加；结果要求结果类型、已做工作、依据和结论，转出辖区必须搜索选择建议单位。撤回填写原因，办结填写总体结论。支队交接申请填写目标丙、原因、已做工作、证据、剩余事项；丙同意时填写从批准生效起所需的最短办理时长，拒绝时填写理由；总队批准时**必须填写丙的新期限**，页面显示该期限是否满足丙的时长条件，若超过整单当前期限还要明确延期理由。A 大队页面绝无“转发给 B 大队”按钮；其跨辖区结果页提示“由支队决定后续任务”。

建议 API：`GET/POST /api/tasks`、`GET /api/tasks/{id}`；分支动作 `/api/tasks/{id}/branches/{branchId}/accept|progress|dispatch|reassign|return|recall|results`；支队交接 `/api/tasks/{id}/branches/{branchId}/transfer-requests`、`.../{requestId}/respond|decide|withdraw`。整单办结为 `POST /api/tasks/{id}/close`；单位候选 `GET /api/tasks/target-units?action=create|dispatch|reassign|transfer|suggest`，除 create 外均需 taskId/branchId 并校验当前承办方，transfer 排除曾承办单位，reassign 排除所有退回单位，suggest 使用提交结果权限并排除本单位。后续任务通过创建请求中的可选 `sourceResultId` 关联，不复制原期限。具体 DTO 和 URL 在实施时由 Java Controller 定稿，经本地 OpenAPI 生成前端类型；不能手改生成文件。客户端不能指定操作者、发送单位、当前责任、状态或完成时间；所有动作 API 二次校验，不能提供通用 `setStatus` 绕过状态机。写请求不自动重试，同一用户意图复用幂等键；失败保留表单输入，409 提示刷新。

详情契约：分支 `allowedActions` 按显示顺序返回 `{code, enabled, reasonCode, reason, transferId}`，整单 `allowedActions` 目前仅含 close。缺功能权限或不满足结构授权条件时不下发；业务前置条件不满足则下发禁用项，原因工厂与写接口共用，文案逐字一致。前端只映射动作名称、主按钮和对应申请，不再用权限或状态推断分支按钮；每个操作区最多一个可用主按钮，禁用原因列在操作区下方。保留旧能力字段以兼容已有测试。没有派发或交接候选时，按钮给出专门的无候选原因。目标支队停用后，总队连拒绝交接也会被单位锁校验阻止，需申请方撤回，这是保留的既有行为。

流程状态标签来自 `task.order.status`、`task.branch.status`、`task.assignment.status`、`task.transfer.status`；退回选项来自 `task.return.reason`。状态项停用不影响流程或历史标签，结果与退回原因的选择项则只用启用项。标签共用会话内字典缓存，业务判断和色调仍按稳定取值。办理记录同刻 CREATE 优先，EXTEND_DUE 合并到同刻批准记录，并显示操作人。

## 8. 事务、实施顺序与验收

创建任务及多目标下发、承接、退回/接回、重新派发、支队交接批准、提交结果与整单办结，各自都在真实用例事务中原子写入业务记录、历史和幂等结果。锁顺序须与系统单位引用锁协调：先锁必要的授权/单位引用，再锁任务与分支/当前承办段，之后写交接、结果、动作和幂等；涉及多个单位按主键排序。不能在持锁事务内调用外部服务。超时先按幂等键查询已提交结果，不能盲目重试。

1. **业务 review**：用本文三个例子逐项核对结果、责任、乙确认的办理时长与总队批准的期限；确认字段上限和结果类型。无需新依赖；如后续确需新增依赖，另按项目规则先提出。
2. **迁移与后端**：检查当时最新 Flyway 编号，追加业务表、COMMENT、约束、索引、结果类型字典和权限/菜单种子；不修改已执行迁移、不建物理外键。实现组织关系、数据范围、状态机、支队交接、明确期限、后续任务关联、并发/幂等；导出当前本地 OpenAPI 并生成前端类型。
3. **前端**：列表、责任树、交接待办、表单和可观察的错误处理。只复用已有依赖；不在浏览器缓存持久化任务敏感正文或权限事实。使用本地合成账号从页面走到 API 和 MySQL。
4. **必要回归**：隔离 MySQL 8.4 验证空库迁移、上一版合成数据升级、实际 COMMENT/索引/约束、UTC 往返、无外键及悬空引用；总队同时发甲乙、支队同时发 A/B、总队直发大队及逆向/跨级拒绝；A 大队跨辖区结果后由支队给 B 建独立期限的新任务；大队平级转发 API 不存在/被拒绝；乙支队交接申请中甲仍负责、丙拒绝后甲仍负责、总队批准后甲结束丙接续同一分支、批准时明确新期限、旧期限和申请时间保留；有未办结子分支不能交接或交结果；全部分支答复或撤回后待办结、发起单位显式填写结论办结；并发双批准只生效一次、幂等重放、回滚无半成品、无关单位 404、管理员不越权。浏览器核对 1366×768 和 1440×900 的亮/暗主题关键链路。静态检查或 mock 不代替真实数据库与权限行为。

## 9. 首版实施落点与复核

- 迁移依次为 `V19__create_task_handling.sql`（七张业务表、字典、菜单、权限）、`V20__normalize_task_permission_codes.sql`（权限码对齐 `模块:资源:动作`，保留权限记录 ID）、`V21__reserve_task_idempotency_command.sql`（事务内预占幂等键）和 `V22__bind_task_page_read_permission.sql`（将旧骨架页菜单改绑正式任务查看权限）；本轮新增 V23 状态与注释、V24 办结及退回字段、V25 NOT_FOUND、V26 按日编号表、V27 状态及原因字典。迁移已分别应用于本地开发库和隔离测试库；已执行文件不回写。
- 后端入口为 `task/TaskController.java`；`TaskService.java` 集中实施功能权限、单位参与范围、状态、期限与事务；`TaskMapper.xml` 是任务表的 SQL 写入口。单位管理通过 `TaskUnitUsageLookup` 拒绝删除已有任务引用的单位及更改其上级。写入事务用 `READ_COMMITTED`，幂等占位在同一事务内落定，失败则整体回滚。
