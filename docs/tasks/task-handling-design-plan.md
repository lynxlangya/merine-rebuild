# 任务处置：数据模型、交互与开发计划

> 状态：2026-09-24 首版已实现，待业务 review。本文保留设计依据与验收口径；第 9 节列出实际落点。总队/支队只向直属下级下发，支队之间可平级交接，大队之间不可交接；支队交接须先由目标支队确认承接，再由总队批准并确定新期限。若业务规则改变，须同步改状态、库表、接口和验收。

## 1. 业务目标与不变量

任务处置是要求接收单位承担一件事并交付明确结果。页面必须回答：任务由谁发起、每个接收分支当前谁负责、何时承接、做过什么、为何退回或交接、最终结果和期限是什么。

1. **直属下发**：总队可同时下发给一个或多个直属支队；支队可同时下发给一个或多个直属大队。总队不能直接给大队；大队不能下发；任何逆向、跨级或非直属“下发”都拒绝。一次多目标下发全成功或全失败。
2. **平级转发只允许支队之间**：仅已承接、当前负责的支队可向另一支队发起交接；大队间不提供转发入口或接口。支队交接不产生新的结果分支，仍是一条责任；甲此前工作和原期限保留。交接生效前甲仍负责，生效后乙负责，甲不再为同一分支另交最终结果。
3. **大队跨辖区反馈**：支队派给 A 大队，A 查明事项进入 B 大队辖区时，A 提交已做工作、依据、去向及未完成部分；支队决定是否给 B **另发任务并单独确定期限**。A 不直接把剩余时限转嫁给 B。
4. **结果与成功不同**：正式结果可以是达成目标、部分完成、查明不在本辖区或无法核实。各责任分支都有明确结果才可整单办结；“流程已办结”不等于“业务目标已达成”，页面同时展示结果类型。承接、进展、退回和交接申请均不算正式结果。
5. **责任不可静默覆盖**：发出后的要求、原期限、历史责任单位和结果不得普通编辑覆盖；每次承接、退回、申请、同意、批准、拒绝、结果和期限调整都有操作者与时间。单位是责任主体，用户是具体操作人。

首版不做附件、催办推送、导出、AI、任务取消和真实业务档案关联；示例中的船舶、嫌疑人员资料仅以合成文本验证，不把真实个人资料导入本地。信息流转模块的签收/反馈/办结状态不直接复用。

## 2. 两种责任关系及示例

**向下下发产生新责任分支；支队平级转发只更换既有分支的承办单位。** 一条分支可以有多段历次承办记录，但最多一条当前有效承办记录，最终只有一份正式结果。

例一：总队建立任务 T，同时发甲、乙支队，得到分支 B1、B2。甲在 B1 下发给直属 A、B 大队，得到子分支 B1.1、B1.2；甲仍负责汇总 B1。A 若查明目标进入 B 的辖区，应提交 B1.1 的调查结果。甲决定是否另建关联的新任务给 B，不能把 B1.1 改派给 B。A、B 的子分支均有结果后，甲才能提交 B1 的汇总结果。

例二：乙支队承接 B2 后查明主要处置辖区属丙支队。乙提交**交接申请**，写明已经做的事、证据、原因和申请时间；丙先确认愿意承接，总队再批准并确定丙的新期限。批准时乙的承办段结束，丙在**B2 原分支**接续办理；不复制 B2，也不要求乙和丙各交一份最终结果。拒绝或尚未批准时乙仍负责。总队对乙早晚承接、何时申请、何时交接均可复核。

例三：支队给 A 大队两天期限，A 第二天才承接，下午发现事项已在 B 辖区。A 的承接时间和原期限不变；A 提交如实结果。如果任务仅要求查明去向，这可以是达成目标；如果要求完成后续处置，则结果标为部分完成或需后续办理。支队若向 B 发新任务，必须给 B 新期限，并以来源结果关联两项任务；B 不承接 A 剩余的半天。

## 3. 截止时间与支队交接规则

- `task_order.initial_due_at` 保存初次要求的整单期限，永不改写；`current_due_at` 是由任务发起单位明确调整后的整单期限。支队间交接涉及总队发出的任务，因此由总队决定是否延期。各承办段独立保存其被要求的 `due_at`，旧承办段的期限不随交接变更。页面并列显示“原期限”和“当前批准期限”，逾期按各段实际承担的期限判断，不能因改期抹掉曾经逾期的事实。
- 正常向下下发时，子分支期限由发送单位明确填写，须晚于创建时刻且不得晚于父分支当前承办期限；直接从任务发起单位创建的一级分支不得晚于整单当前期限。系统不凭剩余半天自动给新单位设半天期限；若剩余时间不够，承办单位应反馈上级，首版由有权单位另建后续任务。首版仅在总队批准支队交接时支持整单延期，不提供独立的通用改期入口，也不硬编码“必须提前 N 小时下发”的考核阈值。
- 支队交接申请只允许一个目标支队；仅适用于原本由总队下发、当前由支队承办的分支。必须填原因、已做工作、证据说明和需继续做的事。存在尚未办结的直属下级子分支时，不允许申请，以免下级办理失去汇总责任。不能交给自己、停用单位、该分支当前负责单位，或曾经承办过同一分支的支队，以免甲 → 乙 → 甲循环推责。
- 丙支队可同意或说明原因拒绝。同意时必须填“从正式交接生效起，至少需要多少办理时间”（分钟数，正整数），而非只答复一个脱离批准时刻的绝对日期；这是丙的承接条件。同意尚未转移责任。总队批准时指定的新期限必须晚于批准时刻，且至少满足丙确认的办理时长；若总队不能接受该时长，应拒绝申请，不能缩短后强行交接。批准还须校验任务仍为 `OPEN`、丙仍可接收、乙仍是当前责任单位、申请未撤回、子分支均已结束；在同一事务将乙承办段置为 `TRANSFERRED`，创建丙的 `IN_PROGRESS` 承办段，更新分支指针并记录期限变化。丙的承接人为其同意申请的用户，`accepted_at` 为总队批准时刻；责任从批准时开始，不追溯到乙申请或丙同意之时，也不要求丙再点击一次“承接”。
- 若丙的新期限晚于整单 `current_due_at`，总队在批准时须一并明确延长整单期限和理由；`initial_due_at` 保留。其他并行分支的承办期限不因整单延期自动改变。丙的新期限必须晚于批准时刻，不得从乙旧期限直接复制。审批拒绝、丙拒绝或申请撤回后乙继续负责，乙可以提交结果或重新申请；申请中乙仍可办理并追加进展，但不能继续向下下发、再次申请交接或提交最终结果，除非先撤回申请，避免审批与办结竞态。
- 交接申请在原期限前后均可提出，但不自动暂停倒计时或免责。乙的承接时间、原期限、申请时间、丙答复时间、总队决定时间单独展示；是否构成延误由业务依据这些事实判断，不让系统把“转发”当作自动合格。

## 4. 状态机与退回

| 对象                             | 状态                                                                                                     | 允许的后续动作                                                                                             |
| -------------------------------- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 整单 `task_order`                | `OPEN` / `COMPLETED`                                                                                     | 初次下发至少一个一级分支；全部分支有正式结果时同事务显式办结。首版不取消、不重开。                         |
| 分支 `task_branch`               | `OPEN` / `COMPLETED`                                                                                     | 始终代表一份须交结果的责任；转发、退回或重新派发不换分支 ID。`COMPLETED` 当且仅当有唯一正式结果。          |
| 承办段 `task_assignment`         | `PENDING_ACCEPT` / `IN_PROGRESS` / `RETURNED` / `TRANSFERRED` / `REASSIGNED` / `COMPLETED`               | 只有当前待承接段可承接或退回；只有当前办理段可追加进展、向下下发、申请支队交接或提交结果。结束段不可再写。 |
| 交接申请 `task_transfer_request` | `AWAITING_TARGET` / `AWAITING_ISSUER` / `APPROVED` / `TARGET_DECLINED` / `ISSUER_REJECTED` / `WITHDRAWN` | 甲提交 → 丙同意/拒绝 → 总队批准/拒绝；生效前甲可撤回。一次分支最多一条未决申请。                           |

**承接前退回**只处理明显错派：当前 `PENDING_ACCEPT` 接收单位须填写原因；原承办段置 `RETURNED`，服务端在同一分支新增发送单位的 `IN_PROGRESS` 承办段，发送单位成为当前责任主体。返回上级是对既有责任的返还，**不是下级向上级发新任务**。原发送单位可重新派给另一个合法直属下级：结束自己的段为 `REASSIGNED`，同分支新建目标段及其明确期限；也可提交有依据的 `UNABLE_TO_VERIFY` 结果。一次退回不新建分支，也不算最终结果，因此“每个分支都有结果”的办结条件保持一致。承接后发现辖区变化不能退回；大队提交结果，支队决定后续任务；支队可按第 3 节申请平级交接。

原发送单位重新派发时，目标必须仍是自己的直属下级，且与被退回单位同层级；不得借 `REASSIGNED` 绕过总队不可直接到大队。退回到总队时总队也须按相同规则处理。重复退回/重新派发形成新的承办段，旧段完整保留；当前责任永远由分支指针确定，而不是按最新时间猜测。一个单位可同时承办同任务的**不同分支**，例如支队既承办父分支，也接回一个被大队退回的子分支。

分支正式提交结果时须填写结果类型、办理经过、明确结论；`OUT_OF_JURISDICTION` 还需说明发现依据及可选建议单位。建议单位只是线索，不能自动产生任务。提交者必须是当前 `IN_PROGRESS` 单位的授权用户，且所有已创建子分支都有结果；同事务写唯一结果、结束当前承办段、置分支 `COMPLETED`，必要时置整单 `COMPLETED` 并记录时间。结果提交后不可覆盖或静默撤回。`COMPLETED` 表示流程交付齐全，不保证每条结果都为 `FULFILLED`。

## 5. 核心库表与约束

业务 owner 为任务处置模块，表名前缀 `task_`。以下是实施字段清单，不是可直接执行的 DDL。所有新表和字段按项目约定写有效 COMMENT，主键为 BIGINT、API ID 为十进制字符串、真实时刻用 UTC `DATETIME(6)`；状态用稳定 code，不用显示中文或 Java ordinal。没有物理外键，引用由写用例锁定校验并纳入悬空引用巡检。迁移只能新增 Flyway 版本，不改已执行文件。

| 表                      | 事实与唯一写入 owner                         | 主要字段、唯一性                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ----------------------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `task_order`            | 一项任务，任务模块                           | `id`、全局唯一 `task_no`、`issuer_unit_id`/`issuer_user_id`、`issuer_unit_name_snapshot`、`title`、`instruction`、`expected_result`（交付目标）、`initial_due_at`、`current_due_at`、`status`、`completed_at`、`version`、可空 `source_result_id`（后续任务的来源）、创建/修改时间。发出后要求、原期限和发起单位名称快照不可普通编辑。                                                                                                                                                                                                                              |
| `task_branch`           | 一个下发目标形成的结果义务，任务模块         | `id`、`task_id`、可空 `parent_branch_id`、`origin_from_unit_id`/`origin_to_unit_id`、`instruction_snapshot`、`expected_result_snapshot`、`current_assignment_id`、`status`、`completed_at`、`version`、创建时间。初次下发的原始发送与接收单位不改写；当前负责单位从当前承办段读取。                                                                                                                                                                                                                                                                                 |
| `task_assignment`       | 同一分支的一段责任，任务模块                 | `id`、`branch_id`、可空 `previous_assignment_id`、`from_unit_id`/`to_unit_id` 及各自发送时的单位名称快照、`source_action` (`DOWNWARD`/`RETURN`/`REASSIGN`/`PEER_TRANSFER`)、`due_at`、`status`、`accepted_by_user_id`/`accepted_at`、可空 `ended_by_user_id`/`ended_at`/`end_reason`、`version`、创建时间。一个分支最多一个活跃段；只有交接批准、退回或重新派发能换当前段。单位后来改名不改变历史交接记录的显示。                                                                                                                                                   |
| `task_transfer_request` | 支队平级交接的申请、接收与总队决定，任务模块 | `id`、`branch_id`、`from_assignment_id`、`target_unit_id`、`reason`、`work_done`、`evidence_summary`、`remaining_work`、`requested_by_user_id`/`requested_at`、`status`、可空 `target_responded_by_user_id`/`target_responded_at`/`target_response_reason`、可空 `target_required_duration_minutes`（丙从批准生效起所需的最短办理时间）、可空 `approved_due_at`/`issuer_decided_by_user_id`/`issuer_decided_at`/`issuer_decision_reason`、`version`。同意必须给正数时长，拒绝必须给原因；每分支同时最多一条未决申请；已决记录不可覆盖。批准前校验来源段仍是当前段。 |
| `task_result`           | 分支唯一正式结果，任务模块                   | `id`、`branch_id` 唯一、`assignment_id`、`outcome_code` (`FULFILLED`/`PARTIAL`/`OUT_OF_JURISDICTION`/`UNABLE_TO_VERIFY` 等稳定 code)、`handling_detail`、`conclusion`、可空 `suggested_unit_id`、`submitted_by_user_id`/`submitted_at`。`assignment_id` 必须是该分支当前承办段；结果不可更新/删除。                                                                                                                                                                                                                                                                 |
| `task_action`           | 追加式业务历史，任务模块                     | `id`、`task_id`、可空 `branch_id`/`assignment_id`/`transfer_request_id`、`action_code`、`actor_unit_id`/`actor_user_id`、可空 `target_unit_id`、可空 `old_due_at`/`new_due_at`、可空 `note`、`occurred_at`。批准交接若同时延长整单期限，要分别记录“交接获批”和“整单延期”两条动作，各自的前后期限有明确对象；不用自由文本代替结构化时间。                                                                                                                                                                                                                            |
| `task_command`          | 可重试写入的幂等结果，任务模块               | `id`、`actor_unit_id`、`action_code`、`idempotency_key`、`request_digest`、`task_id`、可空 `branch_id`、`created_at`；唯一 `(actor_unit_id, action_code, idempotency_key)`。同 key/同语义返回原结果，不同语义 409；重放前仍检查当前访问权。                                                                                                                                                                                                                                                                                                                         |

`task_branch.current_assignment_id` 必须指向同一分支的最新承办段；`task_result.assignment_id`、交接申请的 `from_assignment_id` 也须匹配分支。数据库级唯一约束守住 `task_no`、结果每分支唯一、同分支一条活跃承办段及同分支一条未决交接申请；后两项可用只对活跃状态产生非 NULL 值的生成列 + 唯一键，实际语义需在隔离 MySQL 验证。创建/换责还要锁任务行串行化，不以普通 SELECT 后无条件 UPDATE 保证并发。`CHECK` 守住状态 code、版本非负和基本时间关系；父子组织、身份、数据范围及整单办结属于跨行规则，由事务用例保证。

主要列表和历史索引从查询推导：`task_order(issuer_unit_id, created_at, id)`、`task_branch(task_id, parent_branch_id)`、`task_assignment(to_unit_id, status, due_at, id)`、`task_assignment(branch_id, id)`、`task_transfer_request(target_unit_id, status, requested_at)`、`task_action(task_id, occurred_at, id)`；各关联列有索引。列表先限定授权分支再分页/计数，避免一任务多分支 JOIN 放大 `total`。用合成数据与 EXPLAIN 复核执行计划，不预设大规模性能结论。

## 6. 权限与数据范围

建议功能码：`task:handling:read`、`task:handling:create`、`task:handling:accept`、`task:handling:progress`、`task:handling:dispatch`、`task:handling:return`、`task:handling:submit-result`、`task:handling:transfer-request`、`task:handling:transfer-respond`、`task:handling:transfer-decide`。最后一项只供总队在其发出的支队分支上执行；按钮与后端用例必须同时判权。代码常量、迁移、菜单节点和默认菜单恢复清单保持一致；不提供大队平级转发权限/接口。内置系统管理员的功能码不自动赋予全部业务任务数据范围。

直接参与范围：任务发起单位可看本任务全部分支；当前承办单位可看任务要求、自己负责的分支及其下级结果；曾经承办过的单位可看自己的历史承办段、交接记录和该分支最终结果，但不能继续写。候选丙支队在交接批准前只可看到作出接收决定所需的任务摘要、要求、剩余工作及申请证据摘要，不开放其他无关分支；批准后获得当前分支及必要下级结果。总队作为支队交接的决定者可看该任务与申请全貌。列表、详情、计数、候选单位、交接决定和所有写入都在服务端校验操作权限与数据范围；无关单位猜 ID 返回一致 404。单位筛选只能收窄可见集合。

合法目标按实时 `sys_unit.parent_id` 和层级验证：普通下发必须 `target.parent_id = sender.id` 且层级 +1；支队交接的甲、丙必须都是启用的 2 级支队、同属总队，且不是同一单位。单位停用、账号不属于操作单位、原任务/分支不在参与范围或目标非法均拒绝。已有单位管理对活跃任务涉及的单位删除、修改上级/层级时须联动拒绝；名称修改不回写历史名称快照。当前项目的数据范围尚未实现，任务首版上线必须一并实现任务专属范围，不能只凭菜单码开放全表。

## 7. 页面、表单与接口

沿用 `/collaboration/tasks` 路由，把空骨架替换为：

- **列表**：`待我单位承接`、`我单位办理中`、`我单位发起`、`待我单位回应的支队交接`、`待总队决定的交接`、`已办结`。一行展示任务编号、标题、原/当前截止时间、当前责任单位（可多个分支）、我单位状态、交接待办、最近动作。逾期提示按每段责任期限计算。
- **详情**：独立路由 `/collaboration/tasks/:taskId`，从列表进入并保留分类与页码。先展示本单位待办、任务要求，再按单位层级概览办理状态、原派与最终反馈单位、正式结果类型和结论。展开分支先看完整结果；进行中的分支直接展示办理要求，已完成分支的要求及所有分支的责任、交接经过和期限按需再展开。操作记录默认收起并以中文业务动作展示，不直接显示分支 ID、英文动作码或单位编码。平级交接保留在同一分支，甲的工作摘要不会因丙最终结果而消失。
- **表单**：创建/继续下发可多选直属下级并明确期限；承接是独立确认；承接前退回原因必填；进展仅追加；结果要求结果类型、已做工作、依据和结论。支队交接申请填写目标丙、原因、已做工作、证据、剩余事项；丙同意时填写从批准生效起所需的最短办理时长，拒绝时填写理由；总队批准时**必须填写丙的新期限**，页面显示该期限是否满足丙的时长条件，若超过整单当前期限还要明确延期理由。A 大队页面绝无“转发给 B 大队”按钮；其跨辖区结果页提示“由支队决定后续任务”。

建议 API：`GET/POST /api/tasks`、`GET /api/tasks/{id}`；分支动作 `/api/tasks/{id}/branches/{branchId}/accept|progress|dispatch|return|results`；支队交接 `/api/tasks/{id}/branches/{branchId}/transfer-requests`、`.../{requestId}/respond|decide|withdraw`。后续任务通过创建请求中的可选 `sourceResultId` 关联，不复制原期限。具体 DTO 和 URL 在实施时由 Java Controller 定稿，经本地 OpenAPI 生成前端类型；不能手改生成文件。客户端不能指定操作者、发送单位、当前责任、状态或完成时间；所有动作 API 二次校验，不能提供通用 `setStatus` 绕过状态机。写请求不自动重试，同一用户意图复用幂等键；失败保留表单输入，409 提示刷新。

## 8. 事务、实施顺序与验收

创建任务及多目标下发、承接、退回/接回、重新派发、支队交接批准、提交结果与整单办结，各自都在真实用例事务中原子写入业务记录、历史和幂等结果。锁顺序须与系统单位引用锁协调：先锁必要的授权/单位引用，再锁任务与分支/当前承办段，之后写交接、结果、动作和幂等；涉及多个单位按主键排序。不能在持锁事务内调用外部服务。超时先按幂等键查询已提交结果，不能盲目重试。

1. **业务 review**：用本文三个例子逐项核对结果、责任、乙确认的办理时长与总队批准的期限；确认字段上限和结果类型。无需新依赖；如后续确需新增依赖，另按项目规则先提出。
2. **迁移与后端**：检查当时最新 Flyway 编号，追加业务表、COMMENT、约束、索引、结果类型字典和权限/菜单种子；不修改已执行迁移、不建物理外键。实现组织关系、数据范围、状态机、支队交接、明确期限、后续任务关联、并发/幂等；导出当前本地 OpenAPI 并生成前端类型。
3. **前端**：列表、责任树、交接待办、表单和可观察的错误处理。只复用已有依赖；不在浏览器缓存持久化任务敏感正文或权限事实。使用本地合成账号从页面走到 API 和 MySQL。
4. **必要回归**：隔离 MySQL 8.4 验证空库迁移、上一版合成数据升级、实际 COMMENT/索引/约束、UTC 往返、无外键及悬空引用；总队同时发甲乙、支队同时发 A/B、总队直发大队及逆向/跨级拒绝；A 大队跨辖区结果后由支队给 B 建独立期限的新任务；大队平级转发 API 不存在/被拒绝；乙支队交接申请中甲仍负责、丙拒绝后甲仍负责、总队批准后甲结束丙接续同一分支、批准时明确新期限、旧期限和申请时间保留；有未办结子分支不能交接或交结果；全部分支有结果才整单办结；并发双批准只生效一次、幂等重放、回滚无半成品、无关单位 404、管理员不越权。浏览器核对 1366×768 和 1440×900 的亮/暗主题关键链路。静态检查或 mock 不代替真实数据库与权限行为。
