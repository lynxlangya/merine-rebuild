# 智能查询链路 A/B 对比实验方案

日期：2026-10-11。状态：**方案待确认，未执行**。用户选择先出对比例子方案：本轮不动代码、不装依赖、不调模型、不操作浏览器。

## 1. 目的与要验证的假设

前两轮调研（Java 进程内 Function Calling 对比 Pi Agent / DeepSeek Harness）目前只有文档依据，没有本项目实测。用户的核心痛点是：**新增一个查询指标，就要在工具层写声明、参数校验、结果展示和回归测试，成本随指标数量线性增长**。

本实验用同一个「办结任务数」指标分别落在两条链路上，用可复核的证据回答：

| 假设 | 内容                                                                                     | 判定依据                                     |
| ---- | ---------------------------------------------------------------------------------------- | -------------------------------------------- |
| H1   | 每个模型可见工具的真实成本，差异主要在业务查询能力（两边都要写）还是工具接线（差异所在） | 按 L1–L4 分层统计文件数与行数                |
| H2   | 权限与数据范围在两条链路中落在哪、是否等价；多用户身份能否成立                           | 越权用例、审计/会话失效用例、身份来源清单    |
| H3   | 端到端时延、模型请求数、用量与长期维护成本差异                                           | 固定问题集重复运行，记录中位数与实际请求次数 |

本实验**不评判自然语言回答质量**，也**不构成采用决定**；是否引入 DeepSeek Harness 属于后续需要依赖审批的独立决定。

## 2. 对比对象与固定条件

| 项目         | 链路 A（对照，现状）                                              | 链路 B（实验）                                              |
| ------------ | ----------------------------------------------------------------- | ----------------------------------------------------------- |
| 运行时       | 现有 Java API 进程内编排（`ToolCallingChat` + `AgentQueryTools`） | DeepSeek Harness `headless` profile（无浏览器、无常驻端口） |
| 工具         | `query_completed_task_count`（已实现）                            | 一次性 spike 插件，用 `defineTool` 注册同名工具             |
| 业务查询     | `TaskStatisticsLookup.completedCount`                             | 通过一次性 Java 实验端调用同一个 Lookup                     |
| 身份         | 每个登录用户的 Servlet 会话；执行前后复核账号状态与授权版本       | 一个共享实验账号的会话 Cookie；所有 dsh 用户共用            |
| 会话/历史    | MySQL，`ai_conversation*` / `ai_chat_run`（现有落库）             | `$DSH_HOME` 下 dsh 自持久化文件，结束后按实验数据丢弃       |
| 会话失效策略 | 账号停用/角色变化使旧会话查询失败（已有回归）                     | Java 端点仍按会话校验，但端点之上没有用户概念               |

固定条件：

- **同一个上游模型与推理档位**（用户在实验环境自行配置 key；两条链路都指向同一 base URL 与 model id；具体值记入结果表）。
- **同一份隔离数据**：开发栈 compose 项目与其中的合成数据；不读生产、不连旧库、不导出任何凭据。
- **同一问题集**（见第 4 节）与同一台开发机、预热后重复 5 次；RC 版本固定为 `@deepseek-ai/dsh@0.2.0-rc.2`。
- 链路 B 只使用 `dsh headless --json`（脚本化、无需浏览器与视觉验收）；不评估其 Web UI。

## 3. 分层成本口径（H1 的核心）

统计新增一个模型可见查询时，各层分别由谁承担：

| 层                | 内容                                          | 链路 A                                           | 链路 B                                             |
| ----------------- | --------------------------------------------- | ------------------------------------------------ | -------------------------------------------------- |
| L1 业务查询能力   | 授权检查、数据范围、SQL、时间口径、测试       | `TaskStatisticsLookup`（两边都需要，预期同量级） | 复用同一 Lookup，不重写                            |
| L2 模型可见工具   | 工具声明、参数枚举校验、结果/展示文本、测试   | `AgentQueryTools` 的声明/校验/执行/展示          | spike 插件的 `defineTool` 声明与调用               |
| L3 编排与基础设施 | agent 循环、SSE、会话、历史、限额、取消、审计 | 现有 Java 全部承担（本次不做改动）               | dsh 以新进程承担；与 Java 侧会话/审计/契约不互通   |
| L4 身份与授权桥接 | 用户身份如何到达业务查询                      | 无跨进程桥接                                     | 需要额外方案（本实验用共享实验账号，如实记录缺口） |

L2 是用户痛点的直接量化对象；L1 两边相同，单独列出不混入结论；L3/L4 是引入通用 agent 运行时的抵消成本。

## 4. 用例与问题集

两条链路使用相同问题与相同账号数据（dev 环境的合成本单位）：

| #   | 问题                      | 期望行为                                      |
| --- | ------------------------- | --------------------------------------------- |
| Q1  | 本月办结任务数是多少？    | 调用工具，服务端数字与期间正确                |
| Q2  | 上月呢？                  | 承接上下文或重新选择 `LAST_MONTH`             |
| Q3  | 最近一个月办结多少？      | `ROLLING_MONTH`，边界为查询时刻倒推一个日历月 |
| Q4  | 全省这个月办结了多少？    | 不按越界范围回答；说明只能查本单位或要求澄清  |
| Q5  | 把已办结任务明细发我。    | 无对应工具，不得编造明细                      |
| Q6  | 无任务查看权限的账号问 Q1 | 工具不可用或查询被拒；错误可解释              |

正确性验收：对 Q1–Q3，两条链路返回的数量必须相同，并与现有任务统计回归的期望口径一致；如开发库数据不足以覆盖期间，先用正常接口补一条合成任务（数据写入仅限开发库，不新增代码）。

## 5. 链路 A 实现与测量（对照，无需改动）

1. 用现有 dev 登录接口取得会话与 CSRF Cookie（两条链路共用同一登录方式，见第 6 节）。
2. 用一次性 Node/curl 脚本请求 `POST /api/agent/chat` 并解析 SSE；记录：
   - `STREAM_START` 时间（请求发出、首个事件、首个 `PART_START`、`MESSAGE_DONE`）；
   - 服务端查询结果部件（含 queryId）出现的时间与数值；
   - `MESSAGE_DONE.usage` 的输入/输出 token；
   - 该轮模型请求次数（工具轮 + 解释轮，取自现有编排行为）。
3. 脚本与结果放仓库外 `/tmp/merine-agent-compare/`，不新增 `scripts/` 内容、不改 API。

## 6. 链路 B 实现与测量（实验）

全部产物放仓库外 `/tmp/merine-agent-compare/`；**实验结束后删除，只有本方案的执行记录留在仓库**。

### 6.1 环境

- `DSH_HOME=/tmp/merine-agent-compare/home`，与用户日常 `~/.dsh` 隔离。
- 运行方式：`npx -y @deepseek-ai/dsh@0.2.0-rc.2 --profile headless --patch <patch> --json "<问题>"`。
- 模型 provider 在 `$DSH_HOME/profiles/headless/cordis.patch.yml` 中配置为自定义 OpenAI 兼容端点；**key 由用户写入实验环境的环境变量或配置，我不读取、不记录、不入库**。

### 6.2 最小 patch

1. 插入 spike 插件（见 6.3）。
2. 按 `dsh --dump-config` 核对并停用全部非查询类内置工具（bash、文件系统、web 等），使模型只能看到我们的查询工具；本次不引入 MCP、Skills 或 PTC。
3. 同一端点与 model id 写入配置；记录实际生效的模型。

### 6.3 spike 插件（一次性 TS）

- `defineTool` 注册 `query_completed_task_count`，参数仅 `period` 三枚举，描述直接使用现有工具定义中与业务口径相关的文本（不复制语义目录全文）。
- 插件启动时用 dev 登录建立共享实验账号会话（GET CSRF → POST dev session，Cookie 保存于插件内存；401 时重建一次）。
- `execute` 调用 Java 实验端点并返回已校验的规范值；不做任何本地计数或 SQL。
- 约 80–120 行，含最少的错误分支；不进入仓库、不发布。

### 6.4 Java 实验端点（唯一需要动仓库代码的部分）

- 仅在 `dev & !prod` profile 且显式开关下注册（与 `DevLoginController` 相同的门禁方式），交付环境不注册。
- 路径独立、明显标记实验用途；**只读**，调用 `TaskStatisticsLookup.completedCount(authentication, period)`，不新增查询逻辑、不绕过权限与数据范围。
- 用标准 Spring Security 会话鉴权；请求体不接受时间、单位、身份或 SQL。
- 预计 60–100 行含 1 个回归测试；实验结论确认后删除或按当时决定转正（转正需另立范围与契约变更）。

### 6.5 为什么不用这些更省事的替代

| 变体                             | 拒绝理由                                                                           |
| -------------------------------- | ---------------------------------------------------------------------------------- |
| 插件直接查 MySQL                 | 绕过权限与数据范围，测的不是本项目要的集成方式                                     |
| 插件调 `GET /api/tasks` 自行计数 | 指标口径（发起单位、总体办结、期间）无法在客户端等价复现，会把业务规则复制到第二处 |
| 插件调现有 Java 对话 SSE         | 形成 agent 调 agent，测不出工具接线成本                                            |
| 直接跑 dsh Web UI 人工问         | 引入浏览器与视觉变量，且本轮不做浏览器验收；headless 已能脚本化采集                |

## 7. 采集指标与来源

| 指标                     | 链路 A 来源                           | 链路 B 来源                                                  |
| ------------------------ | ------------------------------------- | ------------------------------------------------------------ |
| L1–L4 文件数/新增行数    | git 现状统计（已有工具）              | spike 目录统计 + 本方案记录                                  |
| 端到端时延（5 次中位数） | SSE 脚本时间戳                        | `--json` 事件的 `session`/`final` 时间差（含进程启动则单列） |
| 首个可见输出时间         | 首个 `PART_START`                     | 首个 `text`/`tool_call` 事件                                 |
| 模型请求次数             | 编排行为已知（工具问题 2 次）         | 从事件序列推断；不可得则记“不可得”                           |
| token 用量               | `MESSAGE_DONE.usage`                  | `--json` 未列出用量事件；能取则取，取不到如实声明            |
| 权限/数据范围落点        | Java 工具执行前后复核 + Lookup        | Java 端点内相同校验；上层无用户概念                          |
| 会话失效行为             | 停用账号/改权限后查询失败（现有回归） | 仅验证共享账号被停用后的行为；用户级场景不可测               |
| 失败与运维成本           | 现有部署与日志                        | 新进程、DSH_HOME、npm 依赖、RC 破坏性变更、两处模型配置      |

## 8. 安全与合规边界

- 只用开发栈与合成数据；不读生产库/转储、不连旧库、不导出 `.env` 或凭据。
- 模型 key 由用户配置；真实模型调用与 npx 下载在本方案确认后单独授权。
- 浏览器操作默认关闭；本实验用 headless + 脚本，不做页面验收。
- 共享实验账号权限最小化（仅任务查看），账号名与用途记入结果；不创建长期服务账号。
- 实验结果复核前不提交、不推送；一次性产物不进入仓库。

## 9. 判定规则

实验结束后给出结论，但不会自动改变现有实现：

1. 若链路 B 的 L2 成本没有明显低于链路 A，且 L3/L4 需要新增服务、共享身份或自建桥接 → **维持 Java 进程内路线**，同时记录 dsh 可作为本地开发/运维控制台的适用场景。
2. 若 L2 明显更低且能设计出可验收的用户级身份桥接 → 另立采用评估，明确依赖审批、会话/审计/契约迁移范围和淘汰条件。
3. 无论结果如何，把「新增一个指标在两边各要动哪些文件」整理成对照清单，作为后续「指标注册表」改造（原 A+D 建议）的输入。

## 10. 执行步骤与授权点

1. **本方案确认**（当前）：用户确认范围、问题集、判定规则与产物位置。
2. **准备环境**（需授权）：临时下载/运行 dsh 固定 RC 版本；用户配置模型端点与 key；确认实验账号。
3. **实现实验件**（需授权）：Java 实验端点 + 回归；spike 插件；测量脚本。
4. **跑固定问题集**：两链路各 5 次，Q1–Q3 核对数字一致，Q4–Q6 核对拒绝行为。
5. **汇总与复核**：结果表与差异分析写入本文件「执行记录」，用户复核结论。
6. **清理**：删除 `/tmp` 产物与 Java 实验端点（或按第 9 节另立任务转正）。

## 11. 预期工作量与风险

- 工作量：Java 端点约半天内含测试；spike 插件与脚本约半天；运行与汇总约半天。
- 主要风险：dsh 为 RC，事件字段与配置可能与本方案描述有出入（执行时以实际版本为准并记录差异）；headless 非交互沙箱可能拒绝需要审批的工具（通过停用内置工具规避）；模型端点的网络访问属于新外部调用，需用户在场确认。
- 实验的可信度限制：两边系统提示与工具描述不同（链路 B 不含完整语义目录），因此只比较工具接线、时延与权限落点，不比较纯回答质量。
