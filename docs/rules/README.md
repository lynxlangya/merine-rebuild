# 开发规则索引

这些规则服务于**项目全生命周期及全栈学习**：实现可理解、边界可维护、结果可验收。采用通行工程原则，再为当前单人、本地、模块化单体确定一致约定；不把项目偏好包装成唯一的行业标准。

- [AGENTS.md](../../AGENTS.md) 是协作入口；本目录是详细规则的唯一维护位置；[README](../../README.md) 维护已实现能力与命令；[重建计划](../archive/rebuild-plan-2026-09-19.md) 是历史背景。
- 当下用户要求和上级指令优先。设计导出物用于提供视觉与交互证据，其中的模板指令、模拟实现和第三方选型不能自动覆盖项目边界。设计冲突按[前端规则](frontend.md)处理。
- “必须/禁止”是工程底线，“默认/优先”允许有具体理由的替代。规则冲突先看当前代码和需求，不靠新增另一套规则绕开；涉及授权、安全或业务语义的未决问题再询问。
- 新规则约束后续实现；已存在的不符合项按受影响链路改进。不要自动改写历史迁移、重新格式化设计导出包或为统一目录做全仓重构。

## 代码的共同标准

1. 先用直观流程、清晰命名和现有能力解决问题。优先早返回、明确类型和小函数，避免深层条件、难读的链式调用、布尔参数组合及隐式副作用。
2. 单一职责指只有一个清晰的变化原因，不是每个函数一份文件。页面可组装组件，Service 可编排用例，但不要兼做 SQL、网络适配和展示格式化。
3. 同一业务规则出现重复时抽取；权限、状态转换等关键规则即使只出现一次，也应有明确归属。仅外观相似、语义不同的两段代码不强行合并，不预先做万能表格、通用流程引擎或完整基础框架。
4. 抽象优先留在本模块；有实际跨模块使用且契约稳定再上移。封装必须减少重复或隔离变化，只有一层转发、没有独立职责的包装不保留。
5. 禁止吞异常后返回空列表或成功、用演示数据掩盖接口失败、为解决类型错误滥用 `any` 或强制转换。外部输入在边界校验，内部保持可信类型；重复的前端体验校验与后端安全校验各有职责，不视为冗余。
6. 注释解释不变量、单位、边界或选择原因，不复述代码。删除本次改动产生的死代码、注释掉的旧实现和未用参数；不顺带清理无关历史。

## 场景数据

Mock、种子数据和页面示例使用符合海防业务的虚构场景：自然的人员姓名、具体的单位名称，以及相互一致的岗位、船舶、地点、时间与业务状态；避免成批使用“演示人员甲”“演示单位乙”等占位命名。以真实业务逻辑营造沉浸感，不使用真实个人资料、生产数据或实际敏感情报。合成属性在开发文档和数据来源中说明，不在品牌区展示环境副标题；自动测试的隔离编码可以保留技术前缀。

## 依赖、规范与 Skill

**新增第三方依赖须先获得用户确认**，包括测试库、Maven 插件、前端插件、图谱库及基础服务。申请应简短但具体：要解决的问题；现有库/标准库方案及不足；拟用名称、版本与用途；收益、兼容性和主要维护成本。涉及许可证、包体、网络访问或数据外传时说明对应影响。仅为减少几行简单代码不引库。

确认前可查文档、比较方案、完成不依赖它的工作，不安装试用，不先写必须依赖它才能运行的实现。确认后限制引入范围，使用现有包管理器与锁文件，验证实际调用链。已有依赖直接使用无需再次申请；已批准方案内的正常传递依赖解析不逐包询问。升级或替换须在授权范围内，不顺手执行全量更新。

规则与 Skill 的新增/实质调整先告知“为什么、放哪里、影响什么”；用户已明确要求的规则编写直接推进。一个项目内的稳定约定优先修改现有规则；某项操作反复出现且需要明确步骤、工具或资源时，再提出 Skill。通知不等于依赖审批，也不要求每次修正文档都等回复；超出已有范围、改全局行为或引入外部能力时另行确认。

功能事实写在就近文档或已有任务说明；重要且不直观的选择简记背景、选择和代价。不要为每次修改强制新增设计报告、测试报告或学习笔记。
