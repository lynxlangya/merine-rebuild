# 测试与验收规则

测试用于消除具体不确定性、守住关键不变量，不追求所有代码都有测试或统一覆盖率。先复用已有有效覆盖，再选择能证明这次行为的最小验证集。

## 1. 什么时候写测试

| 改动/风险                                                         | 要求                                                                                         |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 纯文档、文案、简单样式、无逻辑的组件组合                          | 内容/格式/链接或浏览器检查，不机械补单元测试                                                 |
| 直通 CRUD、简单 DTO/映射                                          | 优先类型检查、现有契约/集成或真实接口联调；独特校验/转换边界有疑问再补测试，不逐 getter 测试 |
| 多分支规则、复杂计算、日期/时区、去重、转换，或无法可靠判断的逻辑 | 编码自动测试，选择正常、边界和反例；必要时先写最小实验验证框架行为                           |
| 权限隔离、状态迁移、事务回滚、幂等、并发、快照、数据丢失风险      | 即使实现看起来简单，也要有相应自动回归证据；已有覆盖有效时不重复新建                         |
| 前端异步竞态、复杂表单、跨页状态、SSE/取消/断连恢复               | 自动测试关键状态转换和失败路径，配合浏览器验证真实交互                                       |
| 真实缺陷修复                                                      | 能稳定自动复现时保留最小回归测试，以同一触发条件证明修复；简单视觉问题使用浏览器对照即可     |

写测试前说得清它要防止的错误。断言业务结果、数据库状态或用户可观察行为，不只断言 mock 调用次数，也不在测试里复刻一份同样的算法。用清晰合成样例，测试名表达条件与预期；不为行数或覆盖率凑断言。

## 2. 选对验证层级

- **纯函数/领域规则**：不启动 Spring 或浏览器，测不变量与边界；单一规则一个清楚用例，避免巨型端到端用例掩盖失败原因。
- **接口与安全**：核对 HTTP 状态、错误体、字段校验、认证/CSRF、直接访问和数据范围；只有 mock Service 的 Controller 测试不能证明真实授权与事务。
- **SQL、迁移、事务与并发**：使用隔离的 MySQL 8.4，验证约束、排序、时区、提交/回滚和并发最终结果。H2 或 mock Mapper 不能作为 MySQL 语义证据。
- **前端状态/组件**：验证查询变更时旧响应不覆盖、重复提交防护、错误后保留输入、主题/抽屉切换不丢状态；优先可观察行为，少依赖组件内部结构。
- **端到端与视觉**：按受影响用户链路连接真实本地前后端，覆盖成功与关键失败；实际操作 1366×768、1440×900 的亮/暗主题。无需把所有分支重复做成 E2E。
- **外部集成**：可控制的替身测超时、断流、重放、取消和结构错误；授权后的真实环境另测真实协议。替身通过不得标记外部平台接入完成。

并发测试使用独立事务/连接、可控同步点或屏障，断言只能产生一个合法结果及无半成品；不要用随意 sleep 赌执行顺序。回滚测试注入中途失败并检查最终持久状态；别让测试本身的外层事务掩盖应用边界，跨 HTTP/线程的写入也不会因测试方法回滚就自动清除。

## 3. 隔离与工具选择

- 破坏性验证只对专用合成测试实例/库执行，使用独立账号与明确名称；运行前检查实际连接目标、激活配置和外部调用开关，不因 profile 名叫 test 就视为安全。
- 不清开发库来准备测试，不连接旧项目或生产，不发真实 AI 请求。种子、时钟、随机值可控制，测试独立、可重复；异步使用有上限的等待并释放资源。
- 优先已有工具；缺测试框架时，先提出最小依赖方案并获得确认，再安装。JUnit、Boot 测试 starter、Vitest、Testing Library、Playwright、Testcontainers、ArchUnit 都不是由本规范自动授权的新依赖。
- Spring Boot 4 按所用技术选择测试 starter，并核对当前版本的注解包。MVC 可评估 `spring-boot-starter-webmvc-test`；`@SpringBootTest` 需要 MockMvc 时显式配置 `@AutoConfigureMockMvc`，不照抄 Boot 3 依赖与 import。依据：[Boot 4 测试迁移](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Migration-Guide#upgrading-testing-features)。
- Java 测试放 `apps/api/src/test/java`，确保命名/插件使测试被实际发现；使用 `*IT` 时需明确 Failsafe 等执行配置，不能只建文件就认为 `verify` 会执行。前端测试就近命名 `*.test.ts(x)`，需接入实际 test 命令后才成为自动门禁。
- 新增关键测试时，检查执行报告中的测试数量、跳过与失败，确保主检查入口实际执行它。没有测试、全部跳过或只启动上下文，都不能声称业务回归通过。

## 4. 当前命令及证据边界

以下基于 2026-09-19 的[启动/检查脚本](../../scripts/dev.sh)、[接口冒烟](../../scripts/smoke.mjs)和[契约生成](../../scripts/generate-contract.mjs)。除纯文档检查外，容器内命令需要相应服务已就绪；不默认启动服务来检查文档。

| 命令/操作                                                                                 | 能证明什么                                                  | 不能证明什么                                                                   |
| ----------------------------------------------------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `./scripts/dev.sh check`                                                                  | 前端 TypeScript、Prettier、后端 Maven verify                | 当前 API 没有测试依赖/测试源码；通过不等于业务测试通过，也没有自动契约差异验证 |
| `./scripts/dev.sh build`                                                                  | 前端生产构建和后端 jar 打包                                 | 不是最终交付镜像、容器健康或页面行为验收                                       |
| `docker compose --env-file .env -f infra/compose.yaml exec -T web pnpm contract:generate` | 从当前本地 API 导出 OpenAPI 和 TS 类型                      | 旧进程可能给出旧契约；先启动当前代码，生成后检查差异及真实 JSON                |
| `docker compose --env-file .env -f infra/compose.yaml exec -T web pnpm smoke`             | 当前 bootstrap 经 Vite 代理的读写、参数校验、请求编号和 404 | 每次追加一条 `SMOKE-` 合成记录，不清理；不覆盖登录、授权或后续业务             |
| `./scripts/dev.sh status` + 受影响接口/页面实际操作                                       | 实际容器状态与指定链路行为                                  | 只看状态不证明整套业务正确                                                     |
| 文档链接核对、对变更文件的 Prettier 检查、`git diff --check`                              | 文档内容与格式质量                                          | 不证明应用运行；新增未跟踪文件须另行检查，不能只看 git diff                    |

不要为修复检查结果重排原始设计导出包或其他无关文件。遇到基线问题区分本次引入与原有问题，修复本次影响并复测；必要检查通过后不无依据扩大测试。

## 5. 完成证据

交付用简短说明列出关键改动、实际执行的检查与结果、未验证项。业务改动至少能解释一条完整请求链路，以及本次关键规则为什么可靠；不强制另写测试报告。

遇到不确定行为先做能证伪的测试/实验；如果缺依赖授权或隔离环境，完成其他可做工作并明确阻塞项，不能偷偷引库，也不能把手工推断或静态通过描述为已完成行为验收。
