## 2. 要解决的问题与非目标

当前白名单在数据源抽屉里，只展示名字；视图字段说明没有统一维护入口，任务定义在 Agent 的 `taskDefinition` 中。新页面负责让管理员看清、维护“允许哪些视图、每个字段和指标是什么意思”。

本轮不做：

- 页面内 DDL、SQL 控制台、自动建视图、自动 GRANT 或账号管理；视图继续由新 Flyway 迁移建立，数据库账号由部署管理者授权。
- 字段启停/字段脱敏、行级或单位过滤、登录身份桥、多用户隔离、通用指标公式引擎、强制业务筛选。
- 多数据源路由或 Agent 自选连接。管理页可维护多个数据源，**当前 Agent 仍只使用部署绑定的一个数据源**；编辑其他数据源不等于 Agent 已切换过去。
- 恢复站内助手、开放 Shell/文件工具、扩展信息发送/接收统计。
- 新依赖、新基础服务或无关重构。

重要边界：本轮“管理员”按项目现有 RBAC 定义为获授查询范围管理权限的维护人员；内置管理员通过现有机制拥有权限。不要硬编码登录名或臆造一个现成的 `SystemAdminGuard`。这不改变普通用户的业务数据权限，也不代表所有管理账号能查看全部业务数据。若未来要求“仅内置角色不可委派”，另行明确后端角色门禁和菜单过滤规则。

## 3. 页面与真实生效链路

```text
数据源管理：连接 / 凭据 / 授权检查 / 数据源启停
  → 查询范围：选择数据源 → 刷新可读视图 → 选择允许视图 → 保存范围
                                  └→ 编辑用途、指标说明、字段说明
  → 数据源复检并启用
  → Java 服务间桥：固定数据源 + 当前白名单 + 语义版本/覆盖值
  → Agent：读取真实 schema、合并说明 → 重建受限 SQL → 只读数据库
```

- 白名单唯一维护入口改为「智能体管理 → 查询范围」。数据源抽屉去掉白名单编辑，只显示已选数量和跳转入口。
- 字段全部沿用该视图已开放的真实字段，仅编辑说明；**界面不能用灰色字段或隐藏行冒充字段授权**。要隐藏敏感列，先修改受审查视图及数据库授权。
- 视图“允许查询”勾选先作为表单草稿；保存改变范围后数据源停用，提示“范围已保存，需复检并启用后生效”。不能用一个开关同时表达“被选中”和“实际可用”。
- 展示：数据源启停状态、已选/未选、最近检查及是否过期、最近探测时间、失效/不可确认原因。网络失败不是视图被删除；未知状态不显示为“已失效”。
- 失效元数据保留以便修复；临时移出白名单保留说明；重新选择时复核实际 schema。取消勾选不删除数据库视图，也不撤销数据库账号权限。
- 修改 host/port/database/username（数据目标或身份）时，清空选中范围及语义覆盖，提示需重新选择；避免新库同名视图继承旧库定义。单纯轮换密码保留范围与说明，但仍按现状停用、重新检查；名称/备注变化不清空说明。清空操作及版本在同一事务内完成。

## 4. 数据模型、业务说明与并发

### 4.1 迁移范围

代码目录当前最高编号为 V54；实现开始时重新确认没有并行新增，空闲时使用 V55，不改写已执行的 V53/V54。迁移包含元数据表、语义版本、权限与菜单引导。

继续用 `ai_data_source_view` 作为唯一**执行白名单**。在 `ai_data_source` 增加 `semantic_version INT NOT NULL DEFAULT 0`，有非负约束与有效中文注释。

新增两张表，以下是字段规范，不是可直接复制执行的 SQL：

| 表                                | 字段与约束                                                                                                                                                                                                                                                                              |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ai_data_source_view_meta`        | `id BIGINT` 自增主键；`data_source_id CHAR(36) CHARACTER SET ascii COLLATE ascii_bin`；`view_name VARCHAR(64)`；`display_name VARCHAR(80) NOT NULL DEFAULT ''`；`description VARCHAR(2000) NOT NULL DEFAULT ''`（用途、统计对象、条件、时间、去重、单位）；`updated_at DATETIME(6)` UTC |
| `ai_data_source_view_column_meta` | `id BIGINT` 自增主键；相同类型的 `data_source_id`、`view_name`；`column_name VARCHAR(64)`；`description VARCHAR(300) NOT NULL DEFAULT ''`；`updated_at DATETIME(6)` UTC                                                                                                                 |

两个唯一键分别为 `(data_source_id, view_name)` 和 `(data_source_id, view_name, column_name)`；标识符使用区分大小写的 ASCII 二进制比较，与 Agent 实际接受的 ASCII 名称一致，不静默小写化。现有白名单表保留原约束，遇到它不能区分的同名候选应明确拒绝，不自动合并。所有表/列/索引关联用途写有效注释，不设物理外键；关联字段已有唯一键前缀，不重复建等价索引。不可暴露数字自增主键。

不新增独立元数据实体框架，放在现有 `agent.datasource` owner 下按职责增补 DTO、服务与 Mapper 即可。未来若新增数据源删除用例，应先锁父行并在同一事务删除白名单与两类元数据；本次不新增删除 API。

### 4.2 版本与一致性

- `version` 继续表示连接/范围/启停等现有配置版本；`semanticVersion` 单独表示说明版本。语义修改不 bump `version`，不清除连接检查结果，也不改变数据源启停状态。
- 元数据保存必须带读到的 `version` 和 `semanticVersion`。短事务先锁数据源父行，校验两者，再整体保存指定视图的说明及字段覆盖值、递增 `semanticVersion`、写审计；版本过期返回 409，不能静默覆盖其他管理员的修改。
- 同样内容重复提交为无改动，不重复递增或写成功变更审计；旧版本请求先按冲突处理，不绕过版本检查。前端保持未保存内容，提示刷新比较，不自动覆盖重试。
- 白名单整表替换带 `version`，先去重并校验名称；集合实际变化后递增 `version`、清除检查结果、强制 DISABLED。原样提交保持原状态和版本。保存空集合合法，但数据源不能启用。
- 新增到白名单的视图必须由服务端使用当前已保存连接重新确认可读，不能相信前端提交的探测结果。网络工作在事务外；随后锁父行并核对原 `version`，防止检查旧连接却保存到新连接。纯移除可以不访问目标库，仍失效并停用。
- 语义保存同样校验当前视图/字段存在、名称唯一和体积限制；正常编辑不接受任意不存在的字段。已失效的旧覆盖可保留展示，清除旧覆盖不要求被删除字段重新存在。
- 连接桥下发的连接、白名单、语义和两类版本必须是一个一致快照。网络授权复检在事务外，最终用短事务锁父行，确认版本未变后读取子表并组成响应；不要持数据库锁等待外部连接。并发变化返回冲突，让调用方重新描述，不无限重试。
- 已经拿到授权且开始的查询，沿用现有超时上限完成；本轮不承诺即时取消在途查询。之后的新查询必须重新读当前授权。修改配置不会从历史聊天中抹除已返回的数据。

### 4.3 说明来源与指标语义

合并规则：字段非空覆盖值 > 目标库实际返回的 `COLUMNS.COLUMN_COMMENT` > “未提供说明”。返回 `defaultDescription/overrideDescription/effectiveDescription/descriptionSource` 供管理页区分来源；模型只拿有效说明及来源标签。空串表示取消覆盖，省略与 null 的语义由 DTO 明确，禁止依赖前端猜测。

视图级显示名为空就用视图名；用途/指标说明为空就标记未填写，**不把 `TABLE_COMMENT='VIEW'` 当业务解释**。不承诺所有视图列都能继承底表注释；不解析 `VIEW_DEFINITION` 去猜列血缘，不向浏览器或模型下发视图 DDL、连接凭据。

取消原稿的 `time_column`：同一 `ai_task_summary` 既有发起时间又有办结时间，一个“默认时间”会误导统计。把各指标的规则写清楚即可，首版不另造指标 DSL。缺少定义或时间含义时先澄清，不能按字段名字猜测后给出正式数字。

迁入 `ai_task_summary` 的说明至少完整保留：

- 定义编号 `task.completed-count`、业务修订号 2（与技术 `semanticVersion` 区分）。
- 每行代表整项任务，唯一标识 `task_id`；按整项任务计数，不按分支或反馈次数计数。
- 总体办结条件为 `status = 'COMPLETED'` 且 `completed_at_utc IS NOT NULL`；按该时间筛选。
- `issued_at_utc` 是发起时间，不得代替办结时间；新增任务统计使用发起时间。
- 时间字段存储 UTC，统计表达采用北京时间；本月从北京时间一号零点至服务器当前时间，最近一个月向前推一个日历月，含起点不含终点；继续调用 `get_business_time`。
- 范围仍是部署固定数据源授权视图；“本单位”不能从用户自述身份推断，没有单位身份隔离。

这些文字是模型理解依据，**不构成强制筛选、SQL 白名单或行级权限**。本轮只能保证 SQL 访问边界，不能宣称任意模型 SQL 都自动符合指标口径；管理员需人工核对代表性统计。以后若要求指标完全确定性，再单独设计受控指标执行器。

## 5. 管理接口、发现流程与权限

新增 `agent:scope:read`、`agent:scope:update`，复用 `PermissionGuard` 和现有会话/CSRF。菜单、常量、注册路由和默认菜单恢复逻辑保持一致；权限加入后，旧管理员会话须按现有登录展开机制重新登录获取新码。不要全局注销所有账号来掩盖新权限问题。

| 方法与路径                                  | 作用与权限                                                                                                                                                                                                |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET `/api/agent/query-scopes`               | 分页返回配置摘要（ID、名称、状态、范围数量、版本、检查状态），仅读本项目配置库；`agent:scope:read`                                                                                                        |
| GET `/api/agent/query-scopes/{id}`          | 返回已保存白名单与覆盖值，不主动连接全部目标库；`agent:scope:read`。没有新探测结果时存在性为未知                                                                                                          |
| POST `/api/agent/query-scopes/{id}/inspect` | 显式刷新该数据源可 SELECT 的视图，以及按请求指定单视图读取字段名/类型/可空性/列注释；`agent:scope:read` 且 `agent:datasource:test`                                                                        |
| PUT `/api/agent/query-scopes/{id}/views`    | `{version, views: string[]}`，整体替换白名单；`agent:scope:update`。涉及新增候选时还需 `agent:datasource:test` 执行复检                                                                                   |
| PUT `/api/agent/query-scopes/{id}/metadata` | `{version, semanticVersion, view, displayName, description, columns:[{name, description}]}`；只替换指定视图的覆盖段，其他视图不动；`agent:scope:update`，涉及实时元数据核对时还需 `agent:datasource:test` |

明确规定字段列表是指定视图的**覆盖集合**：未提交的旧字段覆盖会被清除；前端应提交完整覆盖集合，不能把分页或筛选后的可见行当全部字段。保留失效覆盖时也要在集合中明确携带，服务端仅允许保留已存在的失效项，不允许凭空添加。

发现功能复用现有 `DataSourceChecker/DataSourceReadOnlyInspector` 的连接守卫、只读授权判断、超时和并发名额；扩展最小 schema 读取能力，不在 Controller 或新页面另写无保护的 JDBC 连接。源必须已保存，但允许 DISABLED 状态探测，避免“先启用才能选视图、先选视图才能启用”的死循环。探测只读 metadata，不运行用户 SQL，不读取业务样例行。

视图列表分页（建议 50、上限 100），字段按选中视图加载（上限沿用 Agent 的 100 列）；现有允许白名单最多 50 个，不偷偷扩大。探测响应附 `sourceVersion`、`inspectedAt`，管理页只使用当前选中源的响应，切换数据源或连接版本变化时丢弃旧结果；失败只影响当前卡片，不阻塞全部数据源。

“目标不存在”只能由本次成功探测判定；超时、连接失败、权限不明显示“无法确认”。查看已选但已失效视图不代表允许执行它。Agent 查询发现某个已选视图失效时，本轮沿用明确失败、修复白名单再试，不默默查询剩余视图并冒充完整范围。

普通 API 遵循现有成功/失败外壳与 400/401/403/404/409；并发忙、探测失败、版本冲突、元数据过大分别有稳定错误码，错误不能含密码、JDBC 原始连接串或原始异常栈。管理 DTO 不复用含密码的 `ConnectionGrant`。

### 5.1 原数据源 API 必须一起调整

- `Save` 移除 `views`：新建只保存连接、默认空范围且停用；编辑连接时服务端加载并按 §3 规则保留/清空范围，不能把缺省字段转空集合。
- 旧客户端即使仍提交 `views`，也不能通过连接保存接口写白名单；明确忽略该旧字段或返回参数错误，不能保留暗门。同一次发布更新 Web 和契约，提示旧页面刷新。
- 检查已保存数据源时从服务端白名单读取；草稿连接检查可以做授权发现，但不得保存范围。启用仍经 `agent:datasource:toggle-status` 独立判定，范围编辑不会自动启用。
- 白名单变更必须走同一事务写能力，不复制两套规则。修改连接参数时对白名单/说明的清理是该能力的一部分，不增加新写入口。
- 用更新后的 Java DTO 生成 OpenAPI 与 TypeScript；核对 `SaveDataSource`、检查响应和新查询范围 DTO，以及所有调用方。内部桥是 `@Hidden` 独立协议，还须显式更新 Agent 手写校验，不能只生成前端类型就认为兼容。

## 6. 前端最小布局

新增 `apps/web/src/features/query-scopes/`，沿用项目字体、主题、表单和错误处理。菜单为「智能体管理 → 查询范围」，建议 route key `agent.query-scopes`、路径 `/agent/query-scopes`，位于主系统布局，不能误落入独立 `/agent` 对话壳。按现有路由结构核对冲突。

- 数据源卡片/选择区：名称、数据源状态、已选视图数、检查时间，不显示密码；管理页多源不代表 Agent 自动多源。
- 单源视图列表：刷新可读视图、待保存的允许查询勾选、保存范围按钮，明确保存后停用的影响。
- 选中视图详情：显示名、用途/指标说明、字段紧凑表（字段名/类型、数据库默认注释、覆盖输入、有效说明）。不设默认时间选择器。
- 语义和范围分开保存，避免只改说明也把数据源停用；离开有未保存内容的详情时提示。权限不足只读，直接 URL 和接口同样受后端保护。
- 首次操作路径：保存停用数据源 → 刷新候选 → 保存白名单 → 填说明 → 复检并启用 → 新会话核对工具描述。没有视图时明确需要管理员通过迁移及数据库授权准备，不给假成功按钮。

## 7. Agent 协议、安全与切换

### 7.1 下发与执行

连接桥继续固定数据源、Bearer 服务凭据和 `no-store`，只给受信 Agent 服务端，不给浏览器或模型。新增协议版本 `contractVersion: 2`、`semanticVersion` 和 `viewMeta`（视图显示名、说明、字段覆盖值）。Java 只下发当前白名单内的元数据；Agent 用当前账号读取真实 schema 后，忽略不存在字段的覆盖、采用实际列注释补默认，并把状态说明给用户。

`describe_business_data` 返回有效元数据、源 ID/名称、配置/语义版本、获取时间。模型只看到净化后的业务目录；不能把整个桥响应直接 JSON.stringify 给模型。说明按普通数据呈现，禁止把管理员填写的任意文本拼成高优先级系统指令、执行代码或改变工具/权限配置；React 按文本渲染，不使用未净化 HTML。

为阻断“旧描述配新查询”，描述结果生成 `catalogRevision`：由非秘密的源 ID、两类版本、按稳定顺序序列化的当前字段名/类型/有效说明生成摘要。`query_business_data` 增加必填 `catalogRevision`；执行时重新取授权和 schema、重新计算并比较，不一致或缺失则不执行 SQL，要求重新描述并按新定义生成 SQL。该摘要仅用于一致性，不是权限令牌，不能代替每次后端授权。成功结果/审计记录带两类版本和目录摘要，不记录密码或说明全文。旧会话旧参数得到明确升级提示，不执行旧调用。

语义不得扩大 `compileQuery` 的真实字段集合，不新增 JOIN/任意 SQL/变量/函数等能力；时钟工具和只读事务、并发、超时、200 行/20 列/64 KiB 数据结果限制保持。模型称“本单位”时仍须说明没有用户身份隔离。

### 7.2 大小限制与失效

当前桥硬上限是 64 KiB，新增字段不能只按“50 个视图×100 列×300 字符”无限堆积。首版选择有界完整返回：

- 保存时校验该源所有覆盖值组成的 `viewMeta` 序列化 UTF-8 总量不超过 32 KiB（包含名称和 JSON 开销）；同时执行各字段字符上限，不只检查字符数量。
- 桥完整 JSON 仍不超过 64 KiB，服务端先检查再发送；Agent 保留字节上限和逐字段类型、数量、重名、名称格式、版本非负检查。
- Agent 合并真实 schema/默认注释后的模型可见目录也设 64 KiB 上限。超限明确报目录过大、需减少开放范围或缩短说明；不静默截断定义、过滤条件或有效视图。未来规模超出这一界限再引入分视图描述协议，本次不预建检索系统。
- 外部 DDL/注释变更不会自动递增本地语义版本，所以目录摘要包含实际 schema 和有效说明。字段失效可检测，**自由文本中引用了已删字段的含义不能保证自动识别**；页面需提示人工复核，不能宣称已校验所有业务规则。

### 7.3 兼容与现有定义迁移

1. 先增加存储、API 与管理入口，保留旧 `taskDefinition`，现有问答继续工作。
2. 提供一份与 V54 视图对应的任务说明模板，管理员对**明确选择的源**核对数据库与字段后保存。禁止在迁移里写本机数据源 UUID，或仅凭 `ai_task_summary` 同名就给所有来源套海防定义。模板只用于初始化，不做 Agent 第二套运行真源。
3. 确认当前使用的数据源已保存完整定义及必要字段说明后，再切换 Agent 消费配置并删除硬编码。空元数据只说明未配置，不擅自猜指标、不偷回退旧定义。新环境通过同一页面初始化。
4. Java 与 Agent 在本地停止查询后配套升级、重新编译并重启；版本 2 Agent 遇到旧桥应明确拒绝，不恢复任意 SQL 或旧定义。旧 Agent 不具备语义版本校验，因此不能把混跑旧进程当兼容交付。回退需要配套回退两端代码，新增元数据表保留，不删库。
5. 更新 [`agent-readonly-query.md`](../../tasks/agent-readonly-query.md) 的配置顺序和描述/查询协议；新会话由用户验收。管理页维护定义不等于自动创建新业务数据视图。

## 8. 审计、开放问题决定与验收

原稿四个开放问题的结论：

1. **纳入审计**：复用已有 `AuditTrail`。追加范围变更、语义变更、元数据探测事件；记录操作者、源 ID、视图名、变更字段名/数量、旧新版本与结果。失败事件遵循现有机制，不把说明全文、数据库默认注释、密码或结果行写审计。已有数据源新增/修改/启停/检查事件不重复写。
2. **不做预览 SQL**：提供“刷新可读视图/字段”和“有效说明”展示足够；运行查询留在 Agent 现有工具。
3. **不用通用默认筛选提示或 `time_column`**：用途/指标说明保留明确字段映射与条件，权限靠工具和数据库；文字不能保证统计确定性。
4. **不做一键复制所有注释**：实时回退默认注释即可，复制会使注释形成两份真源。新建顺序见 §6。

沿用本会话要求：**实现者不新增、不运行测试文件；类型/编译、契约及本地接口检查与测试套件区分汇报。** 以下是必须交给用户的手工验收项目，不得标记为已通过。本轮文档评审也不运行这些项目。未来若恢复自动回归，应优先覆盖权限、范围变更和并发，勿为覆盖率扩展无关测试。

| 验收场景                                                 | 期望                                                         |
| -------------------------------------------------------- | ------------------------------------------------------------ |
| 全新源没有视图范围                                       | 能保存停用连接、探测候选、选视图，再复检启用，无死循环       |
