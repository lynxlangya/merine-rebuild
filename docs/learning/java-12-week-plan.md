# Java 12 周进阶与全栈交付学习计划

> 适用时间：2026-09-21（周一）至 2026-12-13（周日）
> 投入节奏：每周 8–12 小时
> 当前起点：能借助 AI 读懂和修改 Java，但独立设计还需建立体系
> 目标终点：能独立完成并解释一个后端模块，走通需求、表结构、接口、Service、事务、SQL、权限、测试和前端联调

本计划是学习排期，不是项目工期承诺，也不是新的开发规范。与 `docs/rules`、当前代码或用户要求冲突时，以规则和当前实现为准；项目里程碑移动时，只重新映射日期，不改变 Java 能力的推进顺序。

## 0. 对话讲解约定（优先于本计划）

真正的学习主要发生在问答和一起看代码的过程中；下面的 12 周安排只是路线，不是每轮回答都要套用的模板。

每次回答 Java 相关问题时，按这个顺序讲：

1. **一句话结论**：先说它解决什么问题，再展开。
2. **前端类比**：能用 React、TypeScript、浏览器请求链类比时，先给你熟悉的锚点。
3. **项目真实链路**：用当前仓库的文件和调用顺序说明，不脱离项目讲抽象概念。
4. **逐步执行**：从请求、数据或状态变化的角度一步步走，标出输入、输出、异常和边界。
5. **为什么与代价**：解释为什么放在这一层、替代方案是什么、代价是什么。
6. **最小验证**：给出一段代码、一条命令、一个测试或一次浏览器操作，让你能自己确认。

表达约束：

- 第一次出现的术语先用人话解释，再给正式名称；不连续堆框架名词。
- 先讲整体，再讲局部；代码只贴相关片段，不整文件倾倒。
- 说得不清楚时换一种讲法，从页面、请求或数据流重新讲，不重复原话。
- 不确定的内容明确说不确定，并用当前代码、测试或运行结果验证。
- 你可以随时打断并说“这里没懂”“换个例子”“从头讲”“先只看链路”或“先不讲原理”。

## 1. 目标与边界

### 1.1 一句话目标

从“AI 生成后能看懂”变成“AI 生成后能判断、能改、能排障，关键代码能自己重写，并能向客户或团队解释为什么这样做”。

### 1.2 起点、终点与证据

| 能力       | 起点                                   | 12 周后的可验证表现                                                                                           |
| ---------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 请求链路   | 能指出页面调用哪个接口                 | 能在不看 AI 的情况下讲清 `页面 → API → Controller → DTO → Service → Mapper → SQL → MySQL`，并说明失败在哪一层 |
| Java 语言  | 能读 record、集合、Stream 和异常       | 能用 Java 21 的清晰类型、异常和集合表达业务规则，不滥用 `Map<String, Object>` 或无职责包装                    |
| Spring     | 能跟着现有代码读 Controller 和 Service | 能解释 Bean、依赖注入、配置、Validation、异常处理、过滤器和事务代理的作用                                     |
| 数据与 SQL | 能看懂简单表结构和查询                 | 能设计约束与索引、写 MyBatis 映射、验证迁移，并解释事务、并发和回滚                                           |
| 权限       | 知道菜单和按钮要控制                   | 能说明功能权限与数据范围的区别，并在后端列表、详情和写入链路执行校验                                          |
| 测试与交付 | 会运行现有命令                         | 能用真实 MySQL、日志和回归测试证明行为，能完成空库迁移、构建和交付演示                                        |
| AI 协作    | 容易接受生成结果                       | 能先写业务约束，再让 AI 生成；能审查、修改、重写和指出至少三个风险                                            |

### 1.3 本轮不解决的问题

- 不追求 JVM 调优、GC 原理、并发编程专家、微服务拆分或分布式事务。
- 不为了学习另建新的业务模块、服务或依赖；业务练习沿用 M1.4、M1.5、M2 已有范围。
- 不连接旧库、生产、外部 AI 服务，不使用真实个人数据或生产数据。
- 不把“能编译”“AI 已生成”“测试全绿”单独当作学习通过；必须同时满足解释、修改和真实验证。

## 2. 学习运行方式

### 2.1 能力阶梯

| 层级            | 表现                                           | 进入下一层前要留下的证据               |
| --------------- | ---------------------------------------------- | -------------------------------------- |
| 1. 能解释       | 能画出一条完整请求链路，说出每层职责和失败路径 | 10 分钟无 AI 讲解，能回答至少 3 个追问 |
| 2. 能修改       | 能改动一个字段、校验、查询条件或状态规则       | 独立修改后，回归测试和真实接口都能验证 |
| 3. 能排障       | 能用日志、测试和 SQL 定位错误发生在哪一层      | 复现一个故障，修复并说明根因           |
| 4. 能独立实现   | 能从需求设计表、接口、Service、SQL 和测试      | 完成一个小模块，别人能按说明运行       |
| 5. 能交付与取舍 | 能解释迁移、权限、事务、并发和部署代价         | 完成一次演示，并明确未验证项和剩余风险 |

### 2.2 每周时间预算

| 时段             |     时长 | 做什么                                                                             |
| ---------------- | -------: | ---------------------------------------------------------------------------------- |
| 概念与定位       |   2 小时 | 只读当前任务需要的 Java、Spring、MyBatis、SQL 或安全知识点，并在仓库中找到对应实现 |
| 参考实现与走查   | 4–6 小时 | 让 AI 生成参考实现；逐层追踪、记录为什么这样写，不直接接受结论                     |
| 无 AI 修改与复现 |   2 小时 | 改一条业务规则、注入一个失败、补或改一个回归测试                                   |
| 验证与复盘       |   1 小时 | 运行规定命令或真实接口；更新本文档的进度、证据、阻塞项和下周调整                   |

如果某周只能投入 8 小时，优先保证“参考实现走查 + 无 AI 修改 + 验证”，概念阅读放到具体问题出现时再补。不要用连续看视频替代运行和调试。

### 2.3 AI 反向学习闭环

每次实现功能前，先写一张任务卡。AI 只能在你给出边界后生成参考实现。

```text
场景：
输入与输出：
状态变化：
权限边界：
失败情况与验收：
```

AI 的输出要求：

1. 实现代码和涉及文件；
2. 请求链路说明；
3. 正常、参数错误、未登录、无权限、冲突和未预期错误；
4. 建议的回归测试；
5. 已知风险、未验证项和需要人工判断的地方。

收到输出后，按顺序完成：

1. **追踪**：从页面或 HTTP 请求追到 SQL，逐层标记输入、输出、校验、事务、权限和异常转换。
2. **质疑**：至少问三次“这一层为什么存在”“去掉会怎样”“哪个错误会被误判”，并回到规则和当前代码核对。
3. **修改**：关闭 AI，改一个业务规则、注入一个失败、补或改一个测试；先独立定位，再让 AI 复看。
4. **重写**：从零重写一段核心 Service 方法或动态 SQL，与 AI 版本对比，保留自己解释得清、测试能证明的部分。
5. **验证**：使用真实 MySQL、真实接口或浏览器验证，不只检查类型和编译。

以下内容由人先决定，AI 不得替代：权限规则、状态迁移、数据范围、事务边界、审计要求和验收标准。AI 生成的代码、测试和解释都属于待验证材料。

### 2.4 每周和每阶段的完成标准

每周至少留下四项证据：

- 一个可运行或可重复的改动；
- 一次无 AI 的链路解释；
- 一条实际执行的验证命令或真实接口结果；
- 一条仍未解决的问题和下一周的处理计划。

每两周设一个阶段门槛。任何一项硬门槛未通过，就重复该阶段的关键任务，不进入下一阶段：

- 讲不清请求链路、事务边界或权限位置；
- 离开 AI 无法完成一次小修改和回归验证；
- 出现关键安全、事务、数据一致性或数据丢失问题仍继续推进。

## 4. 阶段执行明细与门槛

### 阶段一：看懂运行中的 Java（第 1–2 周）

**项目目标**：把 M1.4 的权限、数据范围和管理员保护整理成可实现的需求边界，同时建立“能自己讲清楚”的 Java 阅读能力。

**第 1 周：权限模型与 Java 21 基础**

- 阅读现有登录、用户和单位链路，列出“当前只有系统管理员门禁”的具体位置。
- 只补本任务需要的 Java 知识：record、泛型、集合、Stream、异常、注解、包与导入。
- 在仓库外临时工程完成一个三级单位树小练习：使用 record、enum、`Map`、`Set`、自定义异常和至少两个测试，不把练习代码带进仓库。

**第 2 周：两条完整请求链路**

- 从 `AuthController` 到 `AuthService`、账号查询和会话，画出登录链路。
- 从用户列表页面到 `UserAdminController`、`UserAdminService`、`UserAdminMapper`、XML 和 MySQL，画出查询链路。
- 让 AI 生成一份链路说明，但你用自己的话重写，并标出 400、401、403、404、409 和 500 分别由谁负责。
- 人为制造一个 Bean 注入失败或 Validation 失败，独立定位后恢复，并说明错误发生在启动期还是请求期。

**阶段门槛**：无 AI 讲清登录和用户查询两条链路；仓库外小练习通过测试；能定位并修复一个注入的启动或校验错误。

### 阶段二：从表到接口完成第一个模块（第 3–4 周）

**项目目标**：在 M1.4 范围内完成角色管理的第一个可用切片，把“看代码”升级为“能设计并实现一条写入链路”。

**第 3 周：角色查询、新增与编辑**

- 先写角色管理的任务卡：角色字段、唯一编码、状态、可编辑范围、权限边界和冲突语义。
- 让 AI 生成参考实现；你逐层走查 DTO、Controller、Service、Mapper、XML 和错误映射。
- 关闭 AI，手工重写一个 Service 方法和一段动态 SQL，再与生成版本比较。
- 在真实 MySQL 上验证成功、参数错误、资源不存在和唯一性冲突。

**第 4 周：契约与边界**

- 补齐角色查询的分页、排序白名单、状态校验和编辑冲突。
- 解释“先查再插”为什么可能产生竞态；核对唯一约束、条件更新和事务回滚。
- 重新生成 OpenAPI 与 TypeScript 类型，核对前端实际消费的字段，不手改生成文件。
- 让 AI 提出至少三个反例测试，你挑选并实现真正能证明业务约束的用例。

**阶段门槛**：真实 MySQL 验证成功、400、404、409；独立重写的 Service 或 SQL 通过回归；能解释事务在哪里开始、哪里回滚以及为什么。

### 阶段三：权限模型与数据范围（第 5–6 周）

**项目目标**：把“角色编码门禁”推进到可解释的 RBAC 功能权限与单位数据范围，并证明权限在后端生效。

**第 5 周：权限码与角色授权**

- 设计权限码、角色权限关系和授权入口；权限码由业务语义决定，不由 AI 生成后反向补规则。
- 学习 `Authentication`、`GrantedAuthority`、过滤器链和授权守卫的位置，明确菜单和按钮只是体验层。
- 实现角色分配权限的最小链路，验证新增、删除权限和未知权限码的处理。

**第 6 周：单位数据范围**

- 明确首期数据范围：本人、所属单位、下级单位、明确授权的全部范围；组合角色时说明有效范围如何计算。
- 在列表、详情、统计和写入前限定可见集合，确保筛选只能收窄范围，不能扩大权限。
- 验证跨单位读取、跨单位写入、隐藏菜单后直接调接口、不可披露对象的一致性响应。
- 让 AI 生成数据范围测试建议，你独立修改一条范围规则并补拒绝访问回归。

**阶段门槛**：越权读取和写入被拒绝；权限或单位变化使已有会话失效；能解释功能权限、数据范围和系统管理权限为什么不是一回事。

### 阶段四：事务、并发与审计（第 7–8 周）

**项目目标**：让写入链路在重复请求、并发编辑和失败注入下仍然可解释、可恢复。

**第 7 周：并发编辑与管理员保护**

- 学习事务传播、回滚、隔离级别和条件更新，核对 Spring 代理边界。
- 用版本条件更新或明确的行锁保护角色、单位和用户编辑；解释 `WHERE version = ?` 的实际作用。
- 制造两个并发编辑：只能有一个成功，另一个得到明确冲突，不覆盖新版。
- 验证“不能停用或移除最后一个可用管理员”的保护路径。

**第 8 周：审计、幂等与前端联调**

- 为角色、权限、单位和账号的关键写入记录操作者、动作、对象标识、时间和结果。
- 区分 `requestId`、`idempotencyKey` 和未来 `taskId`；当前没有幂等需求的接口不先造一套框架。
- 角色、单位或授权变化后递增授权版本，验证旧会话在下次请求失效，前端清理身份与查询缓存。
- 连接真实页面验证成功、失败、空数据、无权限和会话失效后的用户可见行为。

**阶段门槛**：并发编辑只有一个合法结果；失败注入不留下半成品；审计记录可核对；授权变化对已有会话生效；能说明隔离级别和条件更新各自解决什么问题。

### 阶段五：验收与交付环境（第 9–10 周）

**项目目标**：把“本地能跑”提升为“从空环境可迁移、可构建、可启动、可诊断”。

**第 9 周：空库迁移与配置**

- 在隔离测试环境从空库执行 Flyway 迁移，核对表、字段注释、约束、索引和已有迁移不被改写。
- 阅读 Maven 生命周期与打包配置，解释 `compile`、`test`、`package`、`verify` 的差异。
- 核对 Profile、环境变量、运行账号权限和 readiness；不允许运行账号拥有 DDL 权限。

**第 10 周：构建、演示与故障定位**

- 使用当前仓库入口构建前端产物和后端 jar，启动应用镜像并完成一次 M1 演示路径。
- 故意注入一个数据库不可达或迁移失败场景，从日志和探针独立定位，不用删卷或改历史迁移绕过。
- 运行契约生成和 Smoke，核对真实 JSON、生成类型和接口文档。
- 说明源码、编译产物、运行容器和命名卷之间的关系，列出未验证项。

**阶段门槛**：从空库和构建产物完成 M1 演示；能定位一个启动或数据库故障；能解释源码、构建产物和运行环境差异。

### 阶段六：M2 最小数据基础与最终验收（第 11–12 周）

**项目目标**：独立完成一个 M2 后端切片，证明前 5 个阶段形成的能力可以迁移到新数据和新业务。

**第 11 周：数据模型与导入设计**

- 围绕人物、船舶、事件和来源记录写清稳定业务 ID、去重依据、字段冲突、来源时间和权限边界。
- 设计新增迁移、约束和索引，说明哪些字段不能由客户端赋值，哪些事实必须可追溯。
- 让 AI 生成参考表结构和映射；你逐条核对业务语义、唯一性和查询方式。

**第 12 周：独立实现与最终演示**

- 独立设计并实现一张表、一个迁移、一个 Mapper、一个 Service、一个 API 和必要测试。
- 验证重复导入不重复生成实体、冲突可定位、失败不留下半成品，来源记录可打开核对。
- 连接前端完成一次真实查询和写入，核对分页、时间、ID 和数据范围。
- 对比 AI 版本与自己的实现，列出至少三个风险或改进点，并给出下一阶段学习方向。

**阶段门槛**：最终切片能从真实页面走到 MySQL；重复导入、冲突和回滚有可复现证据；能解释关键取舍和剩余缺口。

## 6. 最终验收场景

第 12 周结束时，按以下场景逐项验收；任何一项失败都先记录缺口，不把计划完成说成能力完成。

1. **无 AI 解释**：选一条真实请求，从页面说到 SQL，标出校验、事务、权限、异常转换和数据库约束。
2. **独立修改**：改一条实际业务规则，补最小回归测试，用真实 MySQL 或真实接口证明结果。
3. **独立排障**：制造一个错误密码、越权、版本冲突或迁移失败，使用日志、测试和 SQL 找到根因。
4. **独立实现**：完成 M2 切片，包含迁移、接口、Service、SQL、测试和前端联调。
5. **交付说明**：向他人演示并说明改动、验证结果、未验证项、风险和下一步。
6. **AI 审查**：对比 AI 生成版本，指出至少三个错误、过度设计或未覆盖的边界。
